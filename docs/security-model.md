# Security Model

Romeo security starts with service-layer authorization.

Milestone 1 protects the run path:

- caller must belong to the target organization
- caller must have workspace access
- agent list/read/write operations require explicit `agent` grants unless the caller is an admin; new agent drafts create owner `read/write/run` grants
- caller must own the chat or have an explicit `chat` resource grant
- chat comments require chat write access, and persisted mentions are filtered to known same-org users with direct chat access or chat ownership
- notifications are listed and marked read only for the current authenticated principal
- caller must have access to the selected agent or model
- selected provider and model must be enabled
- API keys must satisfy both scopes and resource access
- local password credentials are stored as Argon2id PHC hashes with failed-attempt lockout metadata, never as plaintext or reversible secrets; legacy scrypt hashes verify only for upgrade compatibility and are rehashed after successful local login
- local TOTP MFA uses encrypted-at-rest secret envelopes, short-lived signed challenge tokens, one-time recovery codes stored only as encrypted salted-hash envelopes, and normal session minting only after password plus MFA verification when active factors exist
- local auth audit metadata records known-user login success, MFA-required, failure class, unknown-principal failure aggregation, and MFA lifecycle events without passwords, TOTP codes, TOTP secrets, raw recovery codes, factor display names, or email values; unknown-email login failures use a disabled per-org `system_local_auth` audit actor and a keyed HMAC identifier hash, not the raw email
- local session cookies use `rms_` tokens stored only as hashes, inherit the creator's scopes, are revocable, and pair `SameSite=Lax` with CSRF origin/fetch-metadata checks on unsafe browser mutations
- OIDC browser login uses authorization code + PKCE with a short-lived signed HttpOnly state cookie, uses package-backed discovery through `openid-client`, validates nonce plus RS256 ID-token issuer/audience/time/signature, and mints the same hashed local session cookie path without returning client secrets to the browser
- OIDC account linking is disabled by default; JIT provisioning rejects email collisions with existing local users and issuer/subject collisions across organizations instead of linking or moving accounts, and `GET /api/v1/governance/identity-lifecycle-policy` exposes that policy plus optional SCIM enablement as metadata-only admin-readable posture
- disabled users cannot authenticate through existing API keys, local session cookies, or OIDC JIT refresh; admin disable also revokes user-owned API keys, user-owned sessions, and active support impersonation sessions created or requested by that user, blocks support impersonation targeting that principal, and blocks approval of pending support requests from disabled requesters
- org/global admin roles are stored on users, reflected in authenticated subjects, and changed only through admin-scoped APIs with repeated target-user confirmation; global-admin assignment or revocation requires an existing global admin, and role changes revoke the target user's API keys and sessions
- the auth-provider catalog exposes provider status, protocol, package target, and global/org configuration scope only; provider secret values are accepted only through managed `secretRef` pointers or the audited `/api/v1/admin/secrets` one-time ingestion path, which stores encrypted `romeo-secret://` envelopes and never supports raw readback; GitHub direct OAuth2 login uses a package-backed Authorization Code + PKCE flow with verified email lookup and optional org/team policy, LDAP/AD login uses package-backed LDAPS or StartTLS-required bind/search through `ldapts`, and SAML login uses package-backed signed-assertion validation through `@node-saml/node-saml`
- auth-provider setting audit metadata records provider IDs and change categories only for enablement, display, login ordering, domain posture, org override posture, disabled reason, OIDC connection/mapping posture, OAuth2 connection/mapping posture, LDAP connection/mapping posture, SAML connection/mapping posture, and secret-ref posture; raw display names, domains, issuer URLs, SAML entry points, SAML entity IDs, SAML assertions, LDAP URLs, bind DNs, search filters, client IDs, secret refs, tokens, provider account IDs, GitHub logins, GitHub org/team names, LDAP directory entries, SAML group names, JWKS URLs, and secret values must not enter audit logs
- GitHub direct OAuth2 login is first-party identity, not delegated connector OAuth reuse. The `/api/v1/auth/oauth2/start?providerId=github` and `/api/v1/auth/oauth2/callback` path stores only short-lived signed PKCE state in an HttpOnly cookie, resolves the client secret server-side through the selected secret resolver, exchanges the code server-side, enforces configured allowed domains, required orgs, required teams, and admin teams before session minting, syncs mapped external groups only for pre-existing Romeo groups, and audits counts/booleans rather than raw GitHub profile, email, org, team, token, or provider response data
- LDAP and Active Directory login is first-party identity, not local password reuse. `POST /api/v1/auth/ldap/login` resolves the service bind password server-side through the selected secret resolver, performs bounded service bind/search, verifies the submitted password only through a user bind attempt, applies allowed-domain, required-group, admin-group, and mapped-group policy, syncs mapped external groups only for pre-existing Romeo groups, and audits counts/booleans plus keyed identifier hashes rather than raw identifiers, passwords, LDAP URLs, DNs, filters, directory entries, or group names. The runtime includes a bounded per-process failed-bind lockout guard; enterprise deployments should still layer gateway or IdP throttling for cross-pod rate limiting.
- SAML login is first-party identity, not an OpenWebUI compatibility path. `GET /api/v1/auth/saml/start` creates signed request state, `POST /api/v1/auth/saml/callback` validates the returned response against the original request, and `GET /api/v1/auth/saml/metadata` returns Romeo SP metadata for IdP setup. The IdP signing certificate is resolved server-side through a managed secret ref; SAML request state uses a bounded replay guard plus an HttpOnly state cookie; mapped SAML groups sync only to pre-existing Romeo groups; audits store counts/booleans and keyed subject hashes rather than raw assertions, certificates, entry points, entity IDs, attributes, or group values.
- SCIM v2 is disabled unless `SCIM_ENABLED=true`; when enabled, `/api/v1/scim/v2` requires normal Romeo authentication plus admin scopes, returns raw SCIM JSON without the Romeo envelope, supports Users and Groups, deactivates users instead of destructive user deletion, revokes user-owned keys/sessions on deactivation, deletes groups only after removing memberships and revoking group-principal grants, and audits only schema/action/resource/count metadata rather than user emails, names, group names, or raw IdP payloads.
- OIDC deprovisioning requires an authenticated admin-scoped caller, active issuer matching, repeated subject confirmation, derived local-user mapping, and sanitized audit metadata with subject hashes rather than raw IdP subject values
- support impersonation sessions support an approval-gated request flow with different-admin approval, requester-active checks at approval time, target-user confirmation, short TTL, explicit true-admin revocation, fixed read-only scopes, hashed reason metadata, sanitized revocation audit metadata, and sanitized per-request support audit events with route-level resource metadata for concrete read attempts
- knowledge-base access requires resource grants; workspace access is required for user-private/workspace tiers, while policy-assigned org/shared tiers can cross workspace boundaries only with explicit `use` grants. Tiered RAG compiles an authorization-filtered retrieval plan before vector or lexical queries run, applies org RAG policy for enabled tiers, result budgets, and org/shared KB assignments, and every vector lookup must carry org/workspace/knowledge-base/source filters plus post-query chunk authorization. Non-admin cross-org shared retrieval additionally requires the subject org policy to assign the external KB to `shared` and the resource-owning org to hold an explicit subject/group `use` grant; unassigned cross-org KBs are skipped even if a grant exists
- org RAG policy allowed embedding provider/model pairs are enforced before provider-backed pgvector indexing, rechecked before embedding persistence when providers echo a model name, and enforced during query-time persisted-vector selection; disallowed query-time embedding groups fall back to lexical retrieval without provider egress
- source deletion for the current pgvector path explicitly clears source embedding rows, chunk rows, and stored source objects, then records metadata-only retention evidence with counts and policy posture instead of object keys, filenames, chunk text, source content, or embedding vectors
- vector-store configuration and database configuration are deployment/runtime concerns; APIs may expose sanitized readiness and posture such as active driver, external driver, configured booleans, credential-ref scheme, namespace/partition policy, and routing-active state, but must not expose or mutate database URLs, vector endpoints, collection names, secret refs, raw query text, chunk text, source documents, or embedding vectors; the current admin RAG posture route is aggregate-only and excludes KB/source names, object keys, job IDs, and job payloads
- admin RAG policy update audits store changed categories and counts only; provider IDs, model names, assigned KB IDs, data-residency tags, query text, corpus names, source object keys, chunk text, and embedding vectors must stay out of audit metadata

Security defaults:

- deny by default
- explicit resource grants
- owner `read/write` chat grants are created when non-admin callers create chats
- stable audit event shape
- stable API error shape
- no arbitrary in-process code execution
- no Open WebUI-style pipelines
- dangerous tools require explicit policy and audit

Enterprise and regulated deployment controls to include before high-assurance GA:

- SSO with phishing-resistant MFA where available, local MFA fallback, SCIM or accepted lifecycle alternative, explicit break-glass policy, and last-admin-path protection
- FIPS-capable crypto posture, KMS/HSM-backed secrets, BYOK or per-org keys where required, key-rotation runbooks, and encrypted local MFA/vector/object storage secrets
- per-org or per-environment data isolation options for Postgres, object storage, vector namespaces, caches, workers, backup buckets, and logs
- immutable audit export to SIEM, WORM-capable retention where required, time synchronization evidence, checksum-chain review, and metadata-only audit defaults. Reviewed target evidence can be recorded with `pnpm evidence:audit-integrity`, mounted through `AUDIT_INTEGRITY_EVIDENCE_PATH`, and read through `GET /api/v1/admin/audit-integrity/posture` / `client.admin.auditIntegrityPosture()` without returning SIEM destinations, raw audit metadata, actor identifiers, payloads, mounted paths, or secrets.
- Kubernetes restricted pod security, signed images, SBOM/provenance, admission policy, vulnerability scanning, NetworkPolicy default deny, explicit egress, mTLS or service mesh where required, and no privileged app containers
- air-gapped and private-network operation, explicit provider egress allowlists, no hidden outbound update checks, and offline bundle verification
- data classification, retention, legal hold, export, deletion, backup-retention limits, and restore evidence across database, object storage, vector stores, logs, and support bundles
- encrypted backup targets for Postgres dumps, WAL archives, object-store backups, and evidence stores, with restore manifest SHA-256 verification and redacted evidence that omits database URLs, presigned URLs, bucket credentials, backup object keys, and KMS key material
- tenant-isolation negative suites for API, worker, object-store, vector-store, connector, support, export, and billing surfaces
- incident response evidence: alert rules, live alert firing, support-bundle redaction, access-review exports, support-session revocation, and DR drills
