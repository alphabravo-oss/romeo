# Docker Compose Deployment

Local Compose provides the core local topology:

- Romeo app
- Postgres with pgvector
- Valkey
- RustFS or S3-compatible object storage
- optional Ollama profile

Compose now starts the app, pgvector Postgres, Valkey, RustFS, an explicit RustFS bucket bootstrap service, and a one-shot migration service. Copy `deploy/compose/.env.example` to `.env` in the repo root or pass it with `--env-file` before shared use, then replace `SESSION_SECRET`, `LOCAL_AUTH_SECRET_ENCRYPTION_KEY`, `MANAGED_SECRET_ENCRYPTION_KEY`, `WEBHOOK_SIGNING_KEY`, database credentials, object-store credentials, and Vault credentials if Vault-backed secret ingestion is enabled with high-entropy values. The example env intentionally lists every Compose interpolation variable; `pnpm smoke:compose:env-contract` fails if `deploy/compose/compose.yml` gains a new `${...}` variable without a matching safe default in the example file. `LOCAL_AUTH_SECRET_ENCRYPTION_KEY` protects encrypted local MFA factors, and `MANAGED_SECRET_ENCRYPTION_KEY` protects encrypted locally managed secret refs created through `/api/v1/admin/secrets`; both should be at least 32 high-entropy characters. `LOCAL_AUTH_SECRET_ENCRYPTION_KEY_PREVIOUS` and `MANAGED_SECRET_ENCRYPTION_KEY_PREVIOUS` are empty by default and should be populated only during the staged rewrap window documented in [Secret Rotation Runbook](./secret-rotation.md). `TENANCY_MODE=single` is the Compose default and is returned from `GET /api/v1/me` as `deployment.tenancyMode`; set `TENANCY_MODE=multi` only when the deployment should expose org/global-scoped admin controls. Use [Secret Rotation Runbook](./secret-rotation.md) for staged OIDC PKCE rotation with `SESSION_SECRET_PREVIOUS`, encrypted MFA/managed-secret envelope rewrap, and coordinated webhook signing-key cutovers.

`REPOSITORY_DRIVER=postgres` selects the composed Postgres-backed Romeo repository and is the required setting for shared or production-like Compose installs. `REPOSITORY_DRIVER=memory` is development-only; the app rejects that combination when `DEV_SEEDED_LOGIN=false` so production cannot silently run on process-local state. The Compose `migrate` service runs `pnpm migrate:postgres` before app startup, using the same migration command intended for Kubernetes jobs.

Use `APP_PORT`, `POSTGRES_PORT`, `VALKEY_PORT`, and `RUSTFS_PORT` to move host bindings away from the defaults when another local service is already using them. The app-internal service names and ports do not change.

Postgres uses `pgvector/pgvector:pg18`. Its named volume mounts at `/var/lib/postgresql`, not `/var/lib/postgresql/data`, because PostgreSQL 18 images create a major-version-specific data directory under that parent path.

To use an external hosted Postgres-compatible database instead of the bundled Compose Postgres service, set `DATABASE_URL` to the managed endpoint and include the external override file:

```sh
docker compose -f deploy/compose/compose.yml -f deploy/compose/external-postgres.compose.yml --env-file .env up -d app
```

The override keeps the same `migrate` and app startup contract, puts the bundled `postgres` service behind an unused `bundled-postgres` profile, and adds `host.docker.internal` resolution for local external-Postgres smoke tests. For real hosted services, require `pgvector`, use provider-recommended TLS in `DATABASE_URL`, prefer `sslmode=verify-full` when the provider supports certificate hostname verification, size provider connection limits for the app plus migration and worker processes, and keep database passwords in the `.env` file or a secret manager rather than shell history. `GET /api/v1/admin/readiness` and `GET /api/v1/admin/postgres/operational-posture` now report sanitized connection-security warnings for remote Postgres URLs without required TLS or certificate verification while omitting the database host, user, password, and URL. Validate the path with:

```sh
docker compose -f deploy/compose/compose.yml -f deploy/compose/external-postgres.compose.yml config
docker compose -f deploy/compose/compose.yml -f deploy/compose/external-postgres.compose.yml --profile backup config
pnpm smoke:compose:external-postgres
```

`POSTGRES_POOL_MAX` caps the app process database pool and defaults to `10`. Use [Romeo Deployment Sizing](./deployment-sizing.md) before raising it or running multiple app processes against a managed database. Compose workers call the app API rather than opening repository pools directly, but migration, validation, backup, restore, and DR drill commands still need database connection headroom while they run.

Compose uses the default tiered-RAG posture: one Postgres/pgvector database with shared row-scoped retrieval. The baseline embedding table is already hash-partitioned by `org_id` for partition-pruned retrieval, but ordinary Compose installs should keep `VECTOR_ISOLATION_MODE=shared_row_scope` unless they intentionally mount live `pnpm review:pgvector-isolation` evidence and claim `pgvector_partitioned_by_org`. `POST /api/v1/knowledge-bases/query` compiles authorized user-private/workspace/org/shared retrieval plans before querying, applies `org_id`, `workspace_id`, `knowledge_base_id`, source visibility, and resource-grant filtering through the existing repository path, and exposes only sanitized posture such as `vectorDriver=pgvector`, `isolationMode=shared_row_scope`, external vector-store driver/config/routing booleans, and namespace policy. `GET/PATCH /api/v1/admin/rag/policy` stores org policy in `system_settings` with no migration churn and can tighten enabled tiers plus default/max budgets for Compose installs; it also exposes an explicit `externalVectorStore` policy for deployment-managed namespace/partition policy, Postgres-authoritative DR/reindex strategy, metadata-only export policy, and restore-validation posture. `GET /api/v1/admin/rag/posture` reports the same default plus aggregate corpus/index/job/fallback counts and sanitized external-store posture without vector endpoints, collection names, namespaces, source object keys, chunk text, embedding vectors, job IDs, or job payloads. `pnpm smoke:compose:tiered-rag` proves this default with one org, multiple workspaces, user-private/workspace/org/shared corpora, service-account-owned corpora, a denied corpus skipped by grant enforcement, metadata-only audit readback, `/me.deployment.tenancyMode` readback, and generated-secret/raw-corpus log redaction. `pnpm smoke:rag-vector:enterprise-contract` adds fast backend contract coverage for the same tiered retrieval path plus RAG policy physical-isolation warnings, deployment-managed Qdrant posture, Qdrant secret resolution, scoped Qdrant filters, and Postgres post-filtering of guessed cross-tenant vector hits without retaining raw corpus or vector-store secrets. No Qdrant, operator-managed partition mapping, vector endpoint, or extra migration file is required for the Compose default. If an operator sets `EXTERNAL_VECTOR_STORE_DRIVER=qdrant`, also set `QDRANT_URL`, `QDRANT_COLLECTION`, `QDRANT_API_KEY_REF`, `QDRANT_TIMEOUT_MS`, and `VECTOR_NAMESPACE_POLICY`; readiness fails incomplete wiring, unsafe Qdrant URLs, or disabled secret resolution, and reports `routingActive=true` only when the runtime adapter is wired, then passes vector-store readiness only after the Qdrant collection health probe succeeds. In that mode Romeo still persists provider embeddings in Postgres for source-of-truth and fallback, while Qdrant receives scoped point upserts with deployment namespace and optional partition tokens, filtered query requests, source-vector delete requests, and source-reindex tombstone requests through the same scoped filter.

`MODEL_PROVIDER_STREAM_TIMEOUT_MS` caps idle model-provider streams and defaults to `60000`. Active provider streams reset the timer on each chunk; stalled providers fail with a metadata-only `provider_stream_timeout` run event instead of persisting raw provider error text. `MODEL_PROVIDER_RETRY_ATTEMPTS` defaults to `1`, `MODEL_PROVIDER_RETRY_BACKOFF_MS` defaults to `250`, `MODEL_PROVIDER_CIRCUIT_FAILURE_THRESHOLD` defaults to `5`, and `MODEL_PROVIDER_CIRCUIT_COOLDOWN_MS` defaults to `60000`. `MODEL_PROVIDER_DISABLED_IDS` is a comma-separated provider ID kill-switch list, and `MODEL_PROVIDER_FALLBACK_MODEL_ID` points at an existing enabled model to use as fallback. Romeo retries only pre-output stream failures/timeouts; once assistant content has emitted, the run fails terminally instead of replaying partial content. The provider circuit breaker fails fast with `provider_circuit_open` after the configured failure threshold. Fallback routing also runs only before assistant content is emitted, and kill-switched primary providers are not called when a valid fallback model is configured. Terminal run events include provider/model IDs and fallback reason metadata only. Live provider outage drills and alert firing remain production-readiness evidence, so tune these values with provider latency, quota, and tenant-facing timeout policy before shared use.

The summary intentionally omits provider base URLs, provider payloads, prompts, and raw provider errors. Treat it as an input to monitoring and runbooks; live provider outage drills and production alert firing still need target-tier evidence.

OpenAI-compatible chat providers can use managed `credentialRef` values such as `env://OPENAI_API_KEY` when `SECRET_RESOLVER_DRIVER` is configured to resolve them. With a resolved credential, Romeo calls the provider's `/chat/completions` SSE stream and records text, usage, and sanitized tool-call request events. Tool-capable provider requests include authorization-filtered tool names, descriptions, and JSON Schemas for enabled agent built-in tools plus agent-bound worker-ready imported OpenAPI operations, but never raw tool arguments, secrets, or hidden payload values. Single or batched non-approval built-in model-requested tools execute inline through the run-scoped tool service and resume provider generation with bounded tool result content. Model-requested imported OpenAPI operations validate the `{ parameters, body }` envelope and enqueue metadata-only `tool.operation.dispatch_request` jobs using the operation row ID as the tool name; jobs, audits, and run events store key names, run linkage, subject posture, and dispatch metadata only. When `TOOL_DISPATCH_PAYLOAD_STORE_DRIVER=object-store` and `TOOL_DISPATCH_PAYLOAD_ENCRYPTION_KEY` is set, Romeo stores model-provided and API-provided operation payloads as AES-GCM encrypted object-store envelopes before queueing and exposes only `managed_encrypted_object_store` plus an object key in worker claim responses. The deployable worker can claim managed-payload jobs without a payload file and read the raw execution payload only through the active-lease payload API. Approval-required model tool calls move the run into `waiting_tool_approval`, expose a server-issued `approvalRequestId`, and resume OpenAI-compatible provider generation after approved inline run-scoped tool execution. Worker-backed imported operations move the run into `run.waiting_tool_dispatch`, resume OpenAI-compatible provider generation after sanitized worker completion/failure readback using the dispatch job ID as the synthetic continuation call ID, and cancel linked queued/running dispatch jobs when the run is cancelled. Terminal runs reject future run-scoped tool execution, and cancelling a suspended approval or dispatch wait appends a terminal `run.cancelled` event. Live egress/log evidence remains open deployment work. With no credential ref, the local provider remains deterministic dev echo. With a credential ref that cannot be resolved, runs fail closed with metadata-only provider failure events.

Published agent safety settings can enable `promptInjectionGuard` without deployment-specific infrastructure. In `block` mode, Romeo rejects matching user prompts before chat messages are persisted and omits matching retrieved RAG chunks before composing the provider system prompt. Retrieval run events include only skipped counts and stable category codes, not flagged text, source content, detector patterns, or vector values.

The inbound OpenAI-compatible `GET /api/v1/openai/models`, `GET /api/v1/openai/models/{model}`, `POST /api/v1/chat/completions`, and `POST /api/v1/embeddings` routes plus `/api/models`, `/api/models/{model}`, `/api/chat/completions`, and `/api/embeddings` aliases use the same provider records, model/provider grants, and managed provider credential resolver. Optional OpenWebUI-shaped boot/sidebar bridge routes are disabled by default and require `OPENWEBUI_COMPATIBILITY_ENABLED=true`; the default OpenAPI document also omits their bridge-only component schemas. When enabled, the bridge exposes boot/version aliases, authenticated session-user metadata, selected raw chat/folder/tag/sidebar routes, and channel/message SSE routes without a separate Compose secret or additional migration file. These routes exist for reference validation and deliberate integrations only; first-party persistent chat should keep using native Romeo `/api/v1/chats`, `/api/v1/runs`, and run-event streams.

`OBJECT_STORE_DRIVER=s3` selects the S3-compatible adapter for RustFS/MinIO/R2-style storage. The default `memory` driver remains useful for local tests and ephemeral development.

The `object-store-init` service creates the configured `S3_BUCKET` before app startup. It uses `MINIO_MC_IMAGE`, which is `minio/mc:latest` in the local example for convenience; pin that image to a reviewed tag or digest before shared self-hosted use.

Native file storage uses the same object-store configuration as chat attachments, browser artifacts, voice artifacts, and managed encrypted tool payloads. Bounded inline `POST /api/v1/files` writes allowlisted bytes through the configured object-store adapter, while `POST /api/v1/files/uploads` creates `status=uploading` metadata and returns a short-lived PUT URL for direct object-store upload. `POST /api/v1/files/uploads/resumable` creates a backend-composed resumable session with short-lived PUT URLs for bounded parts; completion reads the staged parts through the object-store adapter, verifies part sizes plus final size/SHA-256/MIME signature, writes the final object, deletes staged parts, and then marks metadata readable. `GET/POST /api/v1/files/{fileId}/shares` manages read/write file grants, and `GET /api/v1/files/{fileId}/content` streams bytes back only after normal org/workspace/resource-grant authorization. Public file metadata never includes raw object keys or bucket URLs, and direct-upload or part-upload URLs should be treated as transient secrets and kept out of logs. No additional Compose Secret, service, or migration file is required beyond the existing object-store settings.

Valkey uses a named volume and append-only persistence in Compose. Org-level abuse controls are available in Compose through the same authenticated admin API as Kubernetes: `GET/PATCH /api/v1/admin/abuse-controls`. Use it to suspend a tenant, require allowed billing statuses, deny missing-plan cost work, or apply provider/connector/tool/worker-class kill switches during incidents. Enforcement blocks new cost-bearing model runs, tool execution and dispatch, connector sync, workflow run start/approval/resume, knowledge ingestion/reindex/embedding jobs, browser automation worker enqueue/claim, and file uploads while writing metadata-only `abuse_control.enforcement_blocked` audits. This is an app-layer safety boundary for self-hosted and local production-like installs; it should be paired with Valkey-backed distributed quota coordination, billing reconciliation workers, and ingress or reverse-proxy controls when Compose is fronted for shared users.

Compose exposes the same app-level edge controls as the Helm chart through `.env`: `REQUEST_BODY_MAX_BYTES`, file/direct/resumable upload limits, chat attachment limits, `HTTP_RATE_LIMIT_*`, and `EDGE_*`. `TOOL_OPERATION_EXECUTION_DRIVER=disabled` keeps imported OpenAPI, webhook, and MCP tool operation execution fail-closed. Set `TOOL_OPERATION_EXECUTION_DRIVER=http-fetch` only after reviewing the external worker boundary, managed secret value resolution, approval flow, and egress controls. The flag makes readiness previews report `ready_for_worker` only after an admin enables the connector and operation, the import has a sanitized absolute OpenAPI server URL or reviewed HTTPS MCP endpoint, auth is configured where required, and the connector network allowlist is populated. The dispatch endpoint then performs bounded HTTP fetches with `TOOL_OPERATION_FETCH_TIMEOUT_MS` and `TOOL_OPERATION_FETCH_MAX_BYTES`, returning response metadata only and never response bodies or secret values; MCP dispatches are wrapped as `tools/call` JSON-RPC requests from the reviewed manifest metadata. The dispatch-request endpoint queues `tool.operation.dispatch_request` jobs for an external worker; by default Romeo stores only routing metadata and reports `external_worker_secret_store_required`. MCP queued jobs can include a metadata-only transport hint with protocol, request-body mode, MCP tool name, and protocol version so the worker can generate the JSON-RPC envelope without receiving raw endpoint URLs or secrets in the claim. Set `TOOL_DISPATCH_PAYLOAD_STORE_DRIVER=object-store`, `TOOL_DISPATCH_PAYLOAD_ENCRYPTION_KEY` with at least 32 high-entropy characters, and optional `TOOL_DISPATCH_PAYLOAD_STORE_PREFIX` to have the app write encrypted payload envelopes to the configured object store before queueing and report `managed_encrypted_object_store` in enqueue, claim, run-event, and worker-readback metadata. Database jobs, audits, usage records, run events, and model-visible tool results still store only parameter/body key names, payload-storage posture, optional transport metadata, and object-store pointer metadata, never raw values or secret refs. Optional enqueue idempotency keys are stored only as scoped hashes and can safely replay the existing job for retries. Workers must claim a dispatch-request lease before execution and renew it for longer operations. Completion/failure readback is accepted only from the worker that holds an active lease, stores sanitized response/error metadata only, best-effort deletes managed payload objects after terminal readback/cancel/expiry/dead-letter, and rejects replay once terminal. Operators can cancel queued or running dispatch requests through the public API/SDK/CLI; cancellation stores `worker_cancelled`, a stable reason code, actor ID, and timestamps without payload values. Operators can run `romeo tools dispatch-requests-expire` from cron to fail stale queued or lease-timed-out requests with `worker_dispatch_request_expired` and metadata-only reason details. A dispatch request that is reclaimed after three stale worker leases is failed with `worker_attempts_exhausted`, metadata-only `deadLetter` details, and a dead-letter alert in the job operational summary. OAuth client-credentials connectors also require the token URL host in the same connector allowlist; their managed secret value must be JSON containing `clientId` and `clientSecret`, and token responses are bounded without returning or auditing access tokens.

The `tool-dispatch` profile runs `romeo workers tool-dispatch` as a bounded dispatch worker loop. Enable it only after provisioning a scoped `ROMEO_API_KEY`, reviewed egress policy, and either app-managed encrypted payload storage or an external payload/secret store. With no `TOOL_DISPATCH_PAYLOAD_FILE`, the worker claims only `managed_encrypted_object_store` jobs and reads raw execution payloads through the active-lease payload API; app pods still persist only encrypted object-store envelopes plus metadata. Mount local payload-file inputs through `TOOL_DISPATCH_PAYLOAD_DIR` and set `TOOL_DISPATCH_PAYLOAD_FILE` to a path under `/tool-dispatch-payloads` only for legacy external-payload jobs, local smoke, or operator-controlled dry runs. `TOOL_DISPATCH_SECRET_RESOLVER_DRIVER` defaults to `disabled`; set it to `env`, `vault`, `aws-sm`, `gcp-sm`, `azure-kv`, or `cloud` only when the matching `env://`, `vault://`, `aws-sm://`, `gcp-sm://`, or `azure-kv://` refs used by worker auth metadata are backed by injected deployment credentials. Worker auth can be bearer, API-key, or OAuth client-credentials; OAuth payloads provide only the managed secret ref, while token URL, scopes, and client-auth method come from sanitized claim metadata. For MCP Streamable HTTP claims, the worker builds the `tools/call` JSON-RPC body from the claim transport metadata plus the raw payload arguments and sends the MCP protocol/version headers required by the reviewed connector. By default the worker denies local/private literal hosts, DNS-resolved private/link-local/reserved addresses, and Kubernetes service DNS names in addition to requiring HTTPS and failing closed on redirects. Claimed jobs can include sanitized JSON response-schema subsets, and the worker validates bounded response bytes locally while reporting metadata only.

When a Compose deployment intentionally enables external tool dispatch, set `TOOL_DISPATCH_WORKER_ENABLED=true`, set `TOOL_DISPATCH_NETWORK_POLICY_ENABLED=true` only after an equivalent host, proxy, or container egress policy is active, and mount reviewed metadata-only live evidence through `TOOL_DISPATCH_LIVE_EVIDENCE_PATH`. `GET /api/v1/admin/tool-dispatch/posture` reports execution-driver, worker/network-policy, managed-payload, queue, live-evidence, MCP proof booleans/counts, warning, and redaction posture without returning operation hosts, payload values, response bodies, MCP arguments, MCP output, object-store keys, secret refs, token values, evidence paths, or evidence bodies. To let admins paste a secret once and write it directly to Vault instead, send `storageDriver: "vault"` and optional `targetSecretRef: "vault://..."`; configure `VAULT_ADDR`, `VAULT_TOKEN`, optional `VAULT_NAMESPACE`, `VAULT_KV_MOUNT`, and `VAULT_TIMEOUT_MS` on the app service. Romeo writes Vault KV-v2 data only, returns the resulting `vault://` ref, and audits only scheme/driver metadata. Keep `SECRET_RESOLVER_DRIVER=vault` enabled anywhere those returned Vault refs must be resolved at runtime.

`NOTIFICATION_DELIVERY_DRIVER=disabled` keeps user notification delivery as ledger-only records. Set `NOTIFICATION_DELIVERY_DRIVER=configured` when one deployment should route mixed user channels by type: webhook, email, Slack-compatible, Teams-compatible, PagerDuty Events API, and FCM mobile push. In configured mode, `NOTIFICATION_EMAIL_DELIVERY_DRIVER=resend|smtp` selects the email adapter. Single-adapter modes remain available with `webhook`, `resend-email`, `smtp-email`, `slack-webhook`, `teams-webhook`, `pagerduty-events`, or `fcm-mobile-push`. Resend requires `NOTIFICATION_EMAIL_FROM` and `NOTIFICATION_RESEND_API_KEY`; SMTP requires `NOTIFICATION_EMAIL_FROM`, `NOTIFICATION_SMTP_HOST`, and optional `NOTIFICATION_SMTP_USER` / `NOTIFICATION_SMTP_PASSWORD`; PagerDuty channels store only `routingKeyRef` and resolve the routing key through the configured secret resolver at send time. FCM mobile push channels store only a managed device-token `tokenRef`; the deployment service-account JSON is referenced through `NOTIFICATION_FCM_SERVICE_ACCOUNT_REF`, with `NOTIFICATION_FCM_PROJECT_ID`, `NOTIFICATION_FCM_BASE_URL`, `NOTIFICATION_FCM_TOKEN_URL`, and `NOTIFICATION_FCM_TIMEOUT_MS` controlling FCM delivery. Use `romeo-secret://` managed secrets for self-hosted device tokens/service-account JSON, or Vault/cloud refs when those resolvers are configured. `NOTIFICATION_RESEND_BASE_URL`, `NOTIFICATION_RESEND_TIMEOUT_MS`, `NOTIFICATION_SMTP_PORT`, `NOTIFICATION_SMTP_SECURE`, `NOTIFICATION_SMTP_TIMEOUT_MS`, `NOTIFICATION_SLACK_TIMEOUT_MS`, `NOTIFICATION_TEAMS_TIMEOUT_MS`, `NOTIFICATION_PAGERDUTY_EVENTS_URL`, and `NOTIFICATION_PAGERDUTY_TIMEOUT_MS` tune the other adapters. `GET/PATCH /api/v1/admin/notification-policy`, `client.notifications.policy()/updatePolicy(...)`, and `romeo notifications policy/policy-update` store org-scoped delivery enablement, allowed channel types, allowed webhook/Slack/Teams hosts, allowed email domains, and suppressed notification types in `system_settings` without adding a migration. User channel config can also set `enabledNotificationTypes` for per-channel category suppression. Transient notification delivery failures store metadata-only `nextAttemptAt` retry state and can be retried with `romeo notifications retry-due` or the `notification-retry-worker` in the `workers` profile, with `NOTIFICATION_RETRY_INTERVAL_MS` controlling the loop delay. Exhausted or policy-suppressed deliveries record metadata-only dead-letter or disabled reason details instead of copying payload bodies, secret refs, provider responses, or destination values. Delivery payloads, email text, SMTP email text, Slack text, Teams cards, PagerDuty custom details, and FCM data payloads contain IDs and notification metadata only, not comment bodies. Each delivery adapter refuses non-matching channel types before network egress and records the mismatch in the delivery ledger.

`WEBHOOK_SIGNING_KEY` derives per-subscription webhook signing secrets without storing raw webhook secrets. Use a high-entropy value in shared and production environments; rotating it changes existing webhook receiver secrets and must follow the coordinated cutover in [Secret Rotation Runbook](./secret-rotation.md).

Stripe billing webhooks are disabled until `BILLING_STRIPE_WEBHOOK_SECRET` is set. `POST /api/v1/billing/webhooks/stripe` verifies the Stripe HMAC timestamp signature, maps supported customer/invoice/subscription events into Romeo's sanitized external billing event shape, and never stores raw provider payloads. Provider-neutral billing proxy webhooks are disabled until `BILLING_GENERIC_WEBHOOK_SECRET` is set. `POST /api/v1/billing/webhooks/generic` verifies `x-romeo-billing-timestamp` plus `x-romeo-billing-signature` over a sanitized external billing event JSON payload. Signed webhook audit rows use a disabled per-org `system_billing_webhook` actor so Postgres audit foreign keys remain valid without exposing a login-capable principal. Tune `BILLING_STRIPE_WEBHOOK_TOLERANCE_SECONDS` or `BILLING_GENERIC_WEBHOOK_TOLERANCE_SECONDS` only if clock skew requires it, and set `BILLING_WEBHOOK_ORG_ID` when the receiver should target an organization other than the seeded default.

Use `GET /api/v1/billing/entitlements` or `client.admin.billingEntitlements()` to compare the current billing plan quota templates to enforced org quota buckets. If the report shows missing quota buckets or mismatched limits/reset intervals, `POST /api/v1/billing/entitlements/reconcile` or `client.admin.reconcileBillingEntitlements()` repairs the org quotas from the current plan without deleting extra manual quota buckets. The report and audit metadata expose only plan/quota posture, counts, and external customer/subscription presence flags, not raw provider payloads.

`DEV_SEEDED_LOGIN=true` keeps local Compose immediately usable with the seeded admin subject. Set `DEV_SEEDED_LOGIN=false` outside local development; then `/api/v1` application routes require bearer authentication while `/api/v1/health`, `/api/v1/openapi.json`, `/api/v1/docs`, `/api/v1/auth/local/login`, `/api/v1/auth/local/mfa/verify`, `/api/v1/auth/oidc/start`, `/api/v1/auth/oidc/callback`, `/api/v1/auth/oauth2/start`, `/api/v1/auth/oauth2/callback`, `/api/v1/delegated-oauth/callback`, and signature-gated provider webhook paths remain public. If `OPENWEBUI_COMPATIBILITY_ENABLED=true`, the read-only OpenWebUI-shaped boot/version aliases are also public.

The database migration is schema-only. For local development or smoke-test bootstrap, run the explicit seed command after migration:

```sh
docker compose -f deploy/compose/compose.yml run --rm migrate pnpm seed:postgres -- --confirm-development-seed
```

This seed command is idempotent and creates the default local org, workspace, admin user, provider/model catalog, agent, knowledge base, voice profile, chat, retention policy, quota bucket, and grants. It refuses live writes without `--confirm-development-seed` and must not be treated as a production tenant bootstrap.

Local password login is available through `POST /api/v1/auth/local/login`; active TOTP factors require either an inline code or follow-up `POST /api/v1/auth/local/mfa/verify` with the short-lived challenge token. Authenticated users can generate one-time local MFA recovery codes through `POST /api/v1/auth/local/mfa/recovery-codes/generate` after proving an active TOTP factor, and local login/MFA verification can consume one unused recovery code when TOTP is unavailable. Admins and users manage local credentials through the authenticated local auth and user lifecycle APIs. Known-user local login failures and MFA enrollment/confirmation/recovery-code/disable actions write metadata-only audit events without passwords, TOTP codes, TOTP secrets, raw recovery codes, factor display names, or email values. Unknown-email failures still return the same generic login error while writing metadata-only `unknown_principal` audit rows under a disabled per-org `system_local_auth` actor with a keyed HMAC identifier hash instead of the email. `POST /api/v1/admin/secret-rotation/rewrap/preview` and `/api/v1/admin/secret-rotation/rewrap` support staged previous-key rewrap for local MFA envelopes and local `romeo-secret://` managed-secret envelopes; reports return counts and failure codes only, never TOTP secrets, recovery-code values, secret refs, values, user emails, or key material. Keep local auth available as the SSO fallback path unless another tested admin login path is active.

OIDC bearer-token verification is available when both `OIDC_ISSUER_URL` and `OIDC_CLIENT_ID` are configured. Romeo uses `openid-client` for provider discovery, fetches JWKS, verifies RS256 issuer/audience/time/signature, normalizes groups through `OIDC_GROUP_CLAIM`, `OIDC_ADMIN_GROUPS`, `OIDC_GROUP_MAP`, `OIDC_WORKSPACE_GROUP_MAP`, and `OIDC_WORKSPACE_GROUP_PREFIX`, and provisions or refreshes the matching local user record after token verification. Mapped external groups are added as durable memberships only when the target Romeo group already exists; unknown group IDs are skipped and bearer-token login does not delete local memberships. Browser login is available through `GET /api/v1/auth/oidc/start` and `/api/v1/auth/oidc/callback`: the start route sets a short-lived signed HttpOnly PKCE state cookie, redirects the user to the discovered authorization endpoint with `S256`, and the callback exchanges the code with the public client ID, verifies the ID token nonce/signature/issuer/audience, then mints the normal hashed `rms_` local session cookie. Passing `providerId` and optional `orgId` to `/api/v1/auth/oidc/start` selects that global or org-scoped provider card's stored OIDC issuer/client/group mapping config, so a Compose install can enable multiple implemented OIDC IdPs without sharing one issuer.

GitHub direct OAuth2 browser login is available through `GET /api/v1/auth/oauth2/start?providerId=github` and `/api/v1/auth/oauth2/callback`: the start route uses a short-lived signed HttpOnly PKCE state cookie, and the callback exchanges the code server-side through `oauth4webapi`, fetches verified GitHub email/org/team metadata within bounded limits, enforces configured allowed-domain/org/team/admin-team policy, syncs mapped external groups only when matching Romeo groups already exist, and mints the normal hashed `rms_` session cookie. Register `http://localhost:${APP_PORT:-3000}/api/v1/auth/oauth2/callback` with the GitHub OAuth app for local Compose, or the externally reachable `APP_ORIGIN` callback for reverse-proxied installs. LDAP and Active Directory login is available through `POST /api/v1/auth/ldap/login`: configure LDAPS or LDAP with StartTLS, base DN, bind DN, managed bind-secret ref, bounded user/group filters, allowed domains, required groups, admin groups, and group maps through the provider settings API, and restrict directory egress to the approved IdP endpoint.

SAML login is available through `GET /api/v1/auth/saml/start`, `POST /api/v1/auth/saml/callback`, and `GET /api/v1/auth/saml/metadata`: configure an HTTPS IdP entry point, SP entity ID, optional IdP issuer, managed IdP certificate `secretRef`, assertion/response signing policy, subject/email/name/group attributes, required groups, admin groups, and group maps through the provider settings API. Register `http://localhost:${APP_PORT:-3000}/api/v1/auth/saml/callback` with a local IdP for Compose, or the externally reachable `APP_ORIGIN` callback for reverse-proxied installs. SAML request state uses a bounded `system_settings` replay guard plus a short-lived signed HttpOnly state cookie; the callback validates request ID, RelayState, signature policy, assertion age, and mapped identity before minting the normal hashed `rms_` session cookie.

Set `SCIM_ENABLED=true` only when an IdP lifecycle client is approved for this deployment. The SCIM v2 endpoints under `/api/v1/scim/v2` require normal Romeo bearer/session authentication plus `admin:read` or `admin:write`; they are not public callback routes. Enabled SCIM supports Users and Groups with raw `application/scim+json` responses, user create/replace/patch, user delete as deactivation plus user API-key/session revocation, group create/replace/patch, and group delete through transactional membership cleanup plus group-principal grant revocation. Keep SCIM paths behind the same reverse-proxy allowlists, audit review, and service-account key rotation policy used for IdP automation. Run `pnpm smoke:scim:lifecycle-contract -- --output dist/ci/scim-lifecycle-contract-smoke.json` for local route-level evidence that disabled SCIM fails closed and enabled group delete removes memberships, revokes group grants, returns SCIM-shaped 404 readback, and keeps audit/evidence free of raw SCIM identities.

Admins can inspect sanitized SSO posture through `/api/v1/admin/sso-settings`, the app SSO panel, or `romeo sso settings`; this reports status, detected provider preset, issuer host, claim names, and mapping counts without returning client identifiers or secrets. `GET /api/v1/admin/auth-providers/catalog` returns the enterprise provider catalog for the frontend app-store page with global/org scope support and implementation status, `GET/PATCH /api/v1/admin/auth-providers/settings` stores global/org provider policy plus per-provider non-secret OIDC config, GitHub OAuth2 policy, LDAP/AD bind/search policy, and SAML SP/IdP policy through `system_settings`, `POST /api/v1/admin/secrets` stores a one-time pasted secret as either an encrypted local `romeo-secret://...` managed ref or a Vault-backed `vault://...` ref when `storageDriver: "vault"` is configured, and `POST /api/v1/admin/auth-providers/settings/test` tests local/implemented OIDC/GitHub/LDAP/AD/SAML provider cards with metadata-only results. Current implemented entries are local auth, generic OIDC, Keycloak, Google, Azure AD/Entra ID, Okta, Auth0, GitHub direct OAuth2, LDAP, Active Directory, and SAML. Provider secrets are configured as managed `secretRef` pointers only; raw client-secret, LDAP bind-secret, or SAML certificate values are never readable after creation, and deployments can still use external `env://`, `vault://`, `external-secret://`, `aws-sm://`, `gcp-sm://`, or `azure-kv://` refs. Provider icons are frontend static assets keyed by `providerId`. `POST /api/v1/admin/sso-settings/test`, the app SSO test action, and `romeo sso test` validate discovery/JWKS reachability while returning only sanitized status and check codes. Auth-provider connection tests and audits do not return or store raw client IDs, full issuer paths, LDAP URLs, bind DNs, search filters, secret refs, tokens, provider account IDs, GitHub logins, emails, org/team names, LDAP directory entries, LDAP group names, SAML entry points, SAML entity IDs, SAML assertions, SAML certificates, SAML group names, or JWKS URLs. External IdP deprovisioning feeds can call authenticated `POST /api/v1/admin/sso/oidc/deprovision` with an admin-scoped service-account key, active issuer, and repeated OIDC subject confirmation; the endpoint disables the mapped local user, revokes user-owned keys/sessions, and audits only issuer host, subject hash/length, user ID, and revocation category. Guarded destructive directory cleanup runs only through `POST /api/v1/admin/directory-sync`; run `pnpm smoke:directory-sync:contract -- --output dist/ci/directory-sync-contract-smoke.json` for local evidence that preview/apply guardrails, admin/current-caller preservation, stale membership removal, disabled-user credential revocation, and audit redaction hold before connecting a customer directory. `GET /api/v1/governance/identity-lifecycle-policy` exposes the current metadata-only lifecycle decision: account linking is disabled, OIDC/GitHub/LDAP/SAML group sync is additive for known groups, destructive membership sync is disabled, and SCIM reports `disabled` by default or `enabled` with `User` and `Group` resources when `SCIM_ENABLED=true`. Account linking remains intentionally disabled.

Voice providers are disabled by default. Set `VOICE_PROVIDER_DRIVER=dev` only for local deterministic audio checks, or `VOICE_PROVIDER_DRIVER=openai-compatible` with a securely injected API key and approved egress for real TTS/STT. `VOICE_OPENAI_VOICES` is the explicit catalog source for `romeo voices sync` and `romeo workers voice-catalog-sync`; sync imports missing profiles, deduplicates by provider/upstream voice ID, creates caller use grants, and audits counts/provider IDs without storing voice names in audit metadata.

Before using a Compose deployment beyond local development, run:

```sh
docker compose -f deploy/compose/compose.yml config
pnpm review:baseline -- --strict --output dist/release/greenfield-baseline-review.json
DATABASE_URL="postgres://romeo:romeo@localhost:5432/romeo" pnpm validate:postgres -- --dry-run
pnpm --filter @romeo/cli start -- readiness --base-url http://127.0.0.1:3000
```

Run `pnpm review:baseline -- --strict` before accepting a greenfield baseline lock or release candidate. It checks that the single migration file has pgvector setup, required tables/indexes, cascade foreign keys, lifecycle columns, no destructive statements, and no PostgreSQL identifier-length blockers. After the migration service has run, run `pnpm validate:postgres` without `--dry-run` against the Compose Postgres database before traffic or user testing. The readiness report should not show critical failures for `SESSION_SECRET`, `LOCAL_AUTH_SECRET_ENCRYPTION_KEY`, `MANAGED_SECRET_ENCRYPTION_KEY` when `romeo-secret://` refs are configured, Vault writer/resolver settings when Vault-backed `vault://` refs are configured, `WEBHOOK_SIGNING_KEY`, `DEV_SEEDED_LOGIN`, `repository_persistence`, `auth_provider_oidc_config`, `auth_provider_secret_refs`, or `tool_operation_execution` in shared environments. A warning for `auth_provider_local_fallback` means local login was deliberately disabled and another tested admin path must be operational before accepting the deployment.
