# Romeo Public Client and CLI

Romeo exposes `/api/v1` as the stable external API surface. The TypeScript client in `@romeo/api-client` is the first supported SDK and the CLI in `@romeo/cli` uses that SDK for normal platform workflows.

The OpenAPI JSON is available at `/api/v1/openapi.json`; a self-contained HTML endpoint index is available at `/api/v1/docs`. The bootstrap current-user profile, core chat/run records, messages, message attachments, message feedback state, chat comments, file objects, OpenAI-compatible model/chat/embedding payloads, tool approval summaries, approval rejection decisions, run events, and `run.continuing` event payloads have named OpenAPI component schemas so UI and SDK consumers do not need to infer those contracts from examples. The default document is the native Romeo contract and omits optional OpenWebUI-shaped bridge paths and bridge-only schemas. `pnpm check:openapi-route-coverage` verifies every public `/api/v1` route registration has a matching OpenAPI operation before release evidence is accepted. Romeo's native `/api/v1` contracts are authoritative for product UI work; OpenWebUI remains a reference project, not Romeo's implementation target.

Native chat branching is available through `POST /api/v1/chats/{chatId}/fork`, `client.chatApi.fork(chatId, { throughMessageId, title, includeAttachments })`, and `client.forkChat(...)`. The endpoint creates a new same-workspace chat, copies source messages through the selected message inclusive, and can omit attachment metadata with `includeAttachments: false`. It does not copy source runs, comments, approvals, hidden tool payloads, worker jobs, or object-store keys; audit metadata records source IDs and copy counts only.

Assistant-message feedback is available through `GET /api/v1/chats/{chatId}/message-feedback`, `GET|POST /api/v1/chats/{chatId}/messages/{messageId}/feedback`, `client.messageFeedbackList(chatId)`, `client.messageFeedback(chatId, messageId)`, and `client.updateMessageFeedback(chatId, messageId, { rating, reasonCode })`. Use the chat-level list endpoint to hydrate visible message rating controls in one request. `rating` accepts `positive`, `negative`, or `none` to clear the caller's current feedback. The response returns the caller's configured state, optional stable reason code, timestamps, and redaction flags only; it does not return message content, reviewer identity, free-text feedback, or raw usage metadata.

Native collaboration channels are available through `GET|POST /api/v1/collaboration/channels`, `/api/v1/collaboration/channels/direct-messages`, `/api/v1/collaboration/channels/{channelId}/members`, `/api/v1/collaboration/channels/{channelId}/messages`, read-state, pinned-message, reaction, thread, and SSE event routes. The TypeScript SDK exposes these as `client.channels.*` plus convenience helpers such as `client.listChannels()`, `client.createChannel(...)`, `client.channelMembers(...)`, `client.postChannelMessage(...)`, `client.pinChannelMessage(...)`, `client.addChannelReaction(...)`, and `client.channelEvents(channelId)`. These are Romeo-native `{ data }` envelope APIs and are independent of the optional OpenWebUI-shaped `/api/v1/channels/...` bridge.

Native workspace folders are available through `GET|POST /api/v1/folders`, `GET|PATCH|DELETE /api/v1/folders/{folderId}`, `/api/v1/folders/{folderId}/items`, and `/api/v1/folders/{folderId}/shares`. The TypeScript SDK exposes them through `client.collaboration.folders(...)`, `createFolder(...)`, `folder(...)`, `updateFolder(...)`, `deleteFolder(...)`, `folderItems(...)`, `addFolderItem(...)`, and `deleteFolderItem(...)`. Folder records include `parentId`, optional `meta`, optional `data`, and `isExpanded` for sidebar tree state. Parent updates are cycle-checked, names are unique per workspace, and deleting a folder removes folder-item associations while moving child folders to the workspace root; it does not delete chats, agents, or knowledge bases.

Native knowledge-base metadata is available through `GET|PATCH /api/v1/knowledge-bases/{knowledgeBaseId}`. The TypeScript SDK exposes this as `client.knowledge.getBase(knowledgeBaseId)` and `client.knowledge.updateBase(knowledgeBaseId, { name, description })`; `description: null` clears the description. The route uses existing knowledge-base grants and writes metadata-only audits with changed fields and description presence, not KB names or descriptions.

OpenAI-compatible clients can list and retrieve usable models through `GET /api/v1/openai/models` and `GET /api/v1/openai/models/{model}`; `/api/models` and `/api/models/{model}` are also served as raw compatibility aliases. They can call `POST /api/v1/chat/completions` or `POST /api/v1/embeddings`; `/api/chat/completions` and `/api/embeddings` are also served as compatibility aliases. These endpoints return raw OpenAI-compatible JSON or `text/event-stream` chunks rather than Romeo's `{ data }` envelope, require the caller to have `models:use` plus the relevant provider/model grants, resolve provider credentials only through managed secret resolvers, and fail closed without returning raw provider endpoints, raw credential refs, prompt text, or embedding input text in error details. The first compatibility slice accepts model discovery/retrieval, string chat messages, optional function tool definitions, provider-returned function tool calls, and float embeddings; multimodal OpenAI message parts remain intentionally outside these endpoints until the media storage and provider-forwarding security model is extended.

OpenWebUI-shaped boot/sidebar probes are optional bridge shims for reference validation, not the default Romeo product surface. They are disabled unless `OPENWEBUI_COMPATIBILITY_ENABLED=true` is set; the default OpenAPI document and generated Python SDK omit those operations and bridge-only component schemas. Native Romeo endpoints should be used for new UI work unless an integration explicitly targets the opt-in bridge. When enabled, bridge probes are available through `GET /api/v1/openwebui/config`, `GET /api/v1/openwebui/version`, `GET /api/v1/openwebui/version/updates`, authenticated `GET /api/v1/auths/`, and selected chat/folder/tag/channel/message routes; they return raw compatibility-shaped JSON, contain only non-secret metadata, and do not perform outbound update checks. Same-path raw detail routes such as `/api/v1/chats/{id}` remain native Romeo envelope routes, and broader OpenWebUI route parity requires explicit product approval.

## Compatibility Policy

- Keep `/api/v1` backward compatible inside a minor release line.
- Additive response fields are allowed.
- Existing request fields, response fields, event names, and error-envelope fields must not be removed or renamed without a new API version.
- API errors use the stable `{ "error": { "code", "message", "request_id", "details" } }` envelope.
- Streaming run events use server-sent events and carry typed `RunEvent` payloads.
- Webhook deliveries are signed with `x-romeo-signature`, `x-romeo-timestamp`, `x-romeo-event`, and `x-romeo-delivery`.
- Secrets must be passed by managed secret reference where supported; clients must not send raw secret values to connector-auth APIs.

Global tenant administration is available through `GET|POST /api/v1/admin/organizations`, `GET|PATCH /api/v1/admin/organizations/{orgId}`, suspension/reactivation routes, deletion-request/cancel routes, `GET /api/v1/admin/organizations/{orgId}/deletion-finalization-preview`, `POST /api/v1/admin/organizations/{orgId}/deletion-finalization-evidence`, `POST /api/v1/admin/organizations/{orgId}/deletion-finalization/execute`, and `GET /api/v1/admin/tenant-deletion/purge-evidence-posture`. The TypeScript SDK exposes these as `client.admin.tenantOrganizations()`, `createTenantOrganization(...)`, `tenantOrganization(orgId)`, `updateTenantOrganization(...)`, `suspendTenantOrganization(...)`, `reactivateTenantOrganization(...)`, `requestTenantDeletion(...)`, `cancelTenantDeletionRequest(...)`, `tenantDeletionFinalizationPreview(...)`, `recordTenantDeletionFinalizationEvidence(...)`, `executeTenantDeletionFinalization(...)`, and `tenantPurgeEvidencePosture()`. These routes require a global admin, create no migration files, use the existing organization/workspace/user/local-password tables plus `system_settings` lifecycle posture/evidence/result records and optional mounted target evidence, and return metadata/counts only. Finalization evidence stores reviewed control statuses and optional evidence-reference hashes for Postgres, object-store, external-vector, backup, operational-log, support-bundle, and external secret-store deletion coverage. The execute route requires exact org confirmation plus `confirmPermanentDeletion: true`, deletes app-tracked Postgres rows and tracked object-store objects only after all controls are satisfied, and returns class/count/redaction posture without raw evidence refs, evidence bodies, object keys, logs, secrets, or vector values. `TENANT_PURGE_EVIDENCE_PATH` can mount reviewed `romeo.tenant-purge-evidence.v1` output from `TENANT_PURGE_EVIDENCE_REVIEWED=true pnpm evidence:tenant-purge` so the posture route reports storage-class completion without returning mounted paths, evidence bodies, backup locations, log bodies, support bundle bodies, secret values, object keys, or vector values. Releases that claim target purge completion can make this a strict Phase 33 GA gate with `pnpm ga:checklist -- --require-tenant-purge-live` / `GA_REQUIRE_TENANT_PURGE_LIVE=true`; target preflight requires `TENANT_PURGE_EVIDENCE_REVIEWED=true`. External vectors, backups, operational logs, support bundles, and external secret stores remain deployment evidence controls rather than app-returned destructive payloads.

Suspending an organization updates the same abuse-control policy used by cost-bearing APIs. While suspended, Romeo rejects new direct OpenAI-compatible chat/embedding requests, eval provider runs, voice provider requests, runs, tool execution/dispatch, connector sync and scheduled connector creation, workflow run/approval/resume and scheduled workflow creation, knowledge ingestion/reindex/embedding jobs, browser automation worker claim/artifact upload registration, explicit webhook test/retry egress, explicit notification retry egress, and file uploads with `abuse_control_blocked` and metadata-only audit rows.

Desktop and mobile clients should use the same `/api/v1` surface as the web app. `client.deviceAuthorizations.create(...)` issues a short-lived access token plus a refresh token for a named device, `refresh(...)` calls the public `/api/v1/device-authorizations/refresh` route with only the refresh token and rotates both the access API key and refresh token, and `revoke(...)` revokes the current backing API key. Refresh tokens are returned only on create/refresh and are stored server-side only as hashes.

Browser-oriented local sessions are available through `client.sessions.create(...)`, `list()`, and `revokeCurrent()`. Session tokens use the `rms_` prefix, are stored server-side only as hashes, are returned once on creation, and the API sets them as `HttpOnly` `SameSite=Lax` cookies for same-origin web use. Unsafe browser mutations are also checked with fetch metadata plus `Origin`/`Referer` against `APP_ORIGIN` and `EDGE_ALLOWED_ORIGINS`; signed SAML and billing webhook callback paths keep their own replay/signature checks.

Local password auth, local TOTP MFA, and one-time local MFA recovery codes are available through `client.localLogin(...)`, `client.verifyLocalMfa(...)`, `client.localAuthStatus()`, `client.setLocalPassword(...)`, `client.startTotpEnrollment(...)`, `client.confirmTotpEnrollment(...)`, `client.generateRecoveryCodes(...)`, and `client.disableMfaFactor(...)`, with matching `client.sessions.*` methods. Local passwords are stored as Argon2id PHC hashes, legacy scrypt hashes verify only for upgrade compatibility, active TOTP secrets are encrypted at rest, and successful local login/MFA verification mints the normal `rms_` session cookie. A login response can return `mfa_required` with a short-lived challenge token instead of a session when active MFA factors exist; the challenge can be satisfied with either a TOTP code or an unused recovery code. Recovery codes are generated only after the current user proves an active TOTP factor, are shown once, are stored only as encrypted salted-hash envelopes, and are consumed on use. Known-user local login failures write `local_auth.login.failure` audit rows with stable metadata-only failure classes; unknown-email failures return the same generic login error while writing `failureClass: "unknown_principal"` under a disabled per-org `system_local_auth` audit actor with a keyed HMAC identifier hash. MFA enrollment, confirmation, recovery-code generation/use, and disable write factor-type/count metadata only. Passwords, TOTP codes, TOTP secrets, raw recovery codes, factor display names, and email values are not copied into audit metadata.

Browser OIDC login starts with `client.startOidcLogin(...)` or `client.sessions.startOidcLogin(...)`, which calls `GET /api/v1/auth/oidc/start` and returns the provider authorization URL while the API sets a short-lived signed HttpOnly PKCE state cookie. Pass `providerId` and, in multi-org UI, the selected `orgId` for the enterprise auth-provider card flow, for example `client.startOidcLogin({ providerId: "okta", orgId: "org_default", returnTo: "/app" })`; Romeo then uses that provider's stored global or org-scoped issuer/client/group mapping config rather than silently falling back to another provider. The provider redirects back to `/api/v1/auth/oidc/callback`; Romeo exchanges the code without storing a client secret, verifies the ID token nonce/signature/issuer/audience, provisions or refreshes the local user in the signed org scope, and sets the normal hashed `rms_` session cookie before redirecting to the signed relative return path.

GitHub direct OAuth2 login starts with `client.startOAuth2Login(...)` or `client.sessions.startOAuth2Login(...)`, which calls `GET /api/v1/auth/oauth2/start?providerId=github` and returns the GitHub authorization URL while the API sets a short-lived signed HttpOnly PKCE state cookie. The provider redirects back to `/api/v1/auth/oauth2/callback`; Romeo resolves the configured managed client-secret ref server-side, exchanges the code through `oauth4webapi`, fetches verified GitHub email/org/team metadata, enforces configured allowed-domain, required-org, required-team, and admin-team policy, syncs mapped external groups only for known Romeo groups, and mints the same hashed `rms_` session cookie. GitHub login is first-party auth; delegated connector OAuth tokens are not reused for login identity.

Support impersonation is available through short-lived read-only support sessions. The approval workflow uses `POST /api/v1/admin/impersonation/requests`, `client.sessions.requestSupportSession(...)`, and `romeo sessions request-impersonation` to create a sanitized pending request; `approveSupportSessionRequest(...)` / `romeo sessions approve-impersonation` requires a different true admin with `admin:write` before a token is minted. Request and decision state is derived from sanitized audit events, so no extra approval table or migration is needed. Direct `POST /api/v1/admin/impersonation/sessions`, `client.sessions.createSupportSession(...)`, and `romeo sessions impersonate` remain constrained to true admin sessions for break-glass use. Support sessions target a confirmed same-org user, last 5-60 minutes, carry a fixed read-only scope set, are never returned as cookies automatically, and write hashed reason metadata rather than raw reasons. True admins can revoke an audited support session through `POST /api/v1/admin/impersonation/sessions/{sessionId}/revoke` and `client.sessions.revokeSupportSession(...)`; revocation invalidates the backing hashed session token and records sanitized target/session metadata without reason text. `GET /api/v1/admin/impersonation/sessions`, `GET /api/v1/admin/impersonation/requests`, and the matching SDK/CLI methods return sanitized readback without tokens or raw reasons. Authenticated support-session requests write `support.impersonation.request` with route-level resource metadata for concrete read attempts only.

SSO posture, editable OIDC settings, the enterprise auth-provider catalog, persisted global/org provider settings, and connection checks are available through `client.authProviderCatalog()`, `client.authProviderSettings()`, `client.updateAuthProviderSettings(...)`, `client.testAuthProviderConnection(...)`, `client.admin.authProviderCatalog()`, `client.admin.authProviderSettings()`, `client.admin.updateAuthProviderSettings(...)`, `client.admin.testAuthProviderConnection(...)`, `client.admin.ssoSettings()`, `client.admin.updateSsoSettings(...)`, `client.admin.testSsoSettings()`, `romeo sso settings`, `romeo sso update`, and `romeo sso test`. Runtime SSO settings persist in one org-scoped configuration record and override environment defaults for bearer-token verification. Auth-provider settings persist through the shared `system_settings` store as one global policy plus optional org override policies, so the frontend provider app-store page can show inherited `default`, persisted `global`, org override, and effective provider state without a new migration.

Implemented OIDC-family provider settings can store their own non-secret issuer URL, client ID, group claim, admin groups, group maps, and workspace group prefix, so Google, Okta, Keycloak, Entra ID, Auth0, and generic OIDC can be live at the same time with distinct IdPs. GitHub provider settings can store OAuth2 client ID, managed client-secret ref, scopes, allowed domains, required orgs, required teams, admin teams, group maps, and workspace mapping hints. LDAP/Active Directory provider settings can store LDAPS or StartTLS-required LDAP URL, base DN, bind DN, managed bind-secret ref, bounded user/group filters, directory attribute names, allowed domains, required groups, admin groups, group maps, and workspace mapping hints. SAML provider settings can store HTTPS IdP entry point, SP entity ID, optional IdP issuer, managed IdP certificate ref, subject/email/name/group attributes, required groups, admin groups, group maps, workspace mapping hints, assertion age/skew policy, and signed response policy.

LDAP login is available through `client.ldapLogin(...)`, `client.sessions.ldapLogin(...)`, and `POST /api/v1/auth/ldap/login`. SAML login starts through `client.startSamlLogin(...)`, `client.sessions.startSamlLogin(...)`, and `GET /api/v1/auth/saml/start`; the IdP posts the browser back to `POST /api/v1/auth/saml/callback`, and `GET /api/v1/auth/saml/metadata` returns SP metadata for IdP setup. Provider secrets remain managed `secretRef` pointers. Admins may paste a secret once through `POST /api/v1/admin/secrets`, `client.createManagedSecret(...)`, or `client.admin.createManagedSecret(...)`; by default Romeo stores an AES-GCM encrypted envelope in `system_settings` using `MANAGED_SECRET_ENCRYPTION_KEY` and returns a `romeo-secret://...` ref for provider settings. When `storageDriver: "vault"` is supplied, Romeo writes the one-time value to Vault KV-v2 through configured `VAULT_ADDR`, `VAULT_TOKEN`, optional `VAULT_NAMESPACE`, `VAULT_KV_MOUNT`, and `VAULT_TIMEOUT_MS`; `targetSecretRef` may choose a specific `vault://...` ref, otherwise Romeo generates a managed `vault://romeo/managed/...` ref. Vault-backed writes do not persist the encrypted raw value in `system_settings`. Raw secret readback is never available, and existing `env://`, `vault://`, `external-secret://`, `aws-sm://`, `gcp-sm://`, and `azure-kv://` refs remain supported for deployments that manage secrets externally. Staged local MFA and local `romeo-secret://` envelope rewrap is available through `POST /api/v1/admin/secret-rotation/rewrap/preview`, `POST /api/v1/admin/secret-rotation/rewrap`, `client.admin.previewSecretRewrap(...)`, and `client.admin.executeSecretRewrap(...)`; reports return counts, failure codes, and redaction flags only, not TOTP secrets, recovery-code values, secret refs, secret values, user emails, or key material.

Provider icons are frontend-owned static assets keyed by `providerId`. The catalog endpoint returns provider IDs, protocol, `global`/`org` configuration scopes, implementation status, package target, local-fallback posture, JIT posture, and MFA delegation posture. Current implemented entries are local auth, generic OIDC, Keycloak, Google, Azure AD/Entra ID, Okta, Auth0, GitHub direct OAuth2, LDAP, Active Directory, and SAML. `POST /api/v1/admin/auth-providers/settings/test` tests local, implemented OIDC-family, GitHub, LDAP, Active Directory, and SAML provider cards using transient non-secret input, stored per-provider config, or active SSO config. OIDC discovery uses `openid-client`; GitHub OAuth2 uses `oauth4webapi`; LDAP/Active Directory uses `ldapts`; SAML uses `@node-saml/node-saml`; existing token/assertion verification remains fail-closed on issuer/audience/time/signature or request-state/account-linking policy. Reports, tests, and audit metadata return only configuration source, detected preset, host-level status, claim names, mapping counts, provider status, managed secret-ref posture, adapter posture, OAuth2 endpoint posture, LDAP bind/search posture, SAML endpoint/certificate posture, and check codes; they do not return or audit client IDs, tokens, full issuer paths, LDAP URLs, bind DNs, search filters, SAML entry points, SAML entity IDs, SAML assertions, SAML certificates, raw secret values, secret refs, JWKS URLs, provider account IDs, GitHub logins, emails, org/team names, LDAP directory entries, LDAP group names, SAML group names, or provider response bodies. Auth-provider setting update audits also include metadata-only `changeSummary` category arrays for changed provider IDs across global/org scopes, including enable/disable, domain, display, ordering, org policy, OIDC posture, OAuth2 posture, LDAP posture, SAML posture, mapping posture, and secret-ref posture without raw names, domains, issuer URLs, LDAP URLs, SAML URLs, bind DNs, filters, client IDs, or refs. Account linking remains disabled: OIDC/GitHub/LDAP/SAML JIT provisioning fails closed if the incoming email matches a different same-org user or if the derived issuer/subject/provider-account/directory-subject user ID is already owned by another org.

OIDC deprovisioning is available through `POST /api/v1/admin/sso/oidc/deprovision`, `client.admin.deprovisionOidcUser(...)`, and `romeo sso deprovision-oidc`. The caller supplies the OIDC subject twice and may supply the active issuer URL; Romeo requires it to match the configured issuer, derives the local OIDC user ID, disables that user, revokes user-owned API keys and sessions, and audits only issuer host, subject hash/length, user ID, and revocation category. Use an admin-scoped service-account key for IdP lifecycle jobs rather than a personal admin session.

User lifecycle administration is available through `GET /api/v1/users`, `POST /api/v1/users/{userId}/disable`, `PATCH /api/v1/users/{userId}/role`, and `POST /api/v1/users/{userId}/local-password`, with `client.admin.users()`, `client.admin.disableUser(...)`, `client.admin.updateUserRole(...)`, `client.admin.setUserLocalPassword(...)`, `romeo users list`, and `romeo users disable`. Disabling a same-org user sets `disabledAt`, revokes that user's API keys and local sessions, revokes active support impersonation sessions created or requested by that user, blocks future API-key/session/OIDC authentication for that principal, rejects support impersonation targeting disabled users, and rejects approval of pending support requests from disabled requesters. Role changes support `user`, `org_admin`, and `global_admin`, require repeated user confirmation, revoke the target user's API keys and sessions, and require an existing global admin to assign or revoke `global_admin`. Admin-set local passwords use the same local credential store as self-service password changes. Audit metadata records only user IDs, role category, credential-revocation category, and revocation counts, not tokens or profile fields.

Self-service profile updates are available through `PATCH /api/v1/me` and `client.updateMyProfile(...)`. `GET /api/v1/me` is a raw bootstrap response whose `subject` includes the current user's `email` and `name`, and user subjects also include an optional `user` object for profile display. User subjects can update their own email and display name; service accounts and support sessions cannot. Email changes are normalized, checked for same-org conflicts, keep local password login email lookup in sync, and audit only metadata booleans rather than raw email or name values.

## Python SDK

The generated Python SDK lives in `sdks/python` and uses only the Python standard library. Regenerate it from a running Romeo API with:

```sh
pnpm sdk:python -- --openapi-url http://127.0.0.1:3000/api/v1/openapi.json
```

```py
from romeo_client import RomeoClient, OPERATIONS

client = RomeoClient(base_url="http://127.0.0.1:3000", api_key="rmk_...")
print(client.health())
agents = client.list_agents("workspace_default")
chat = client.create_chat("workspace_default", "Python check")
run = client.start_run(chat["id"], agents[0]["id"], "Hello Romeo")
for event in client.stream_run_events(run["id"]):
    print(event["event"])
```

The generated `OPERATIONS` catalog covers the current OpenAPI operations and `RomeoClient.operation(...)` can call any operation by name with path/query/body values.


Supported webhook event types currently include run completion/failure, built-in tool success/failure, knowledge source indexing, quota alerts, and test deliveries. Tool events send sanitized identifiers, risk state, input key names, output key names, and error codes only; knowledge events send source metadata and chunk counts only; quota alerts send bucket scope, metric, used/limit, percent used, and severity. Raw prompts, tool input values, tool outputs, and source content are not included in webhook payloads. Delivery readback APIs expose payload key summaries only. Retries for first-party product events redeliver a stored allowlisted event envelope, while custom `webhook.test` payload values are sent only on the initial test attempt and the retry ledger retains only the redacted key summary.

Agent export documents are versioned JSON. The v1 document includes draft name, base model, system prompt, parameters, memory policy, safety settings, optional voice profile ID, grouped agent access grants, knowledge-base binding IDs, and built-in tool binding IDs/settings. Import validates the caller can use the model, voice profile, knowledge bases, and tools and validates access-grant principals before creating the new draft; unsupported bindings or missing principals are rejected without creating a partial agent. Published version state and prompts from historical versions are not imported by the current v1 document.

Published agent versions snapshot the same compact memory, safety, voice, knowledge, and built-in tool binding state used by export. Version diffs include memory, safety, and binding changes, and rollback restores the selected version's memory, safety, and binding snapshot by re-enabling referenced bindings and disabling bindings absent from that version.

`webhooks retry-due` runs one retry batch and exits. `workers webhook-retry` is the deployable scheduler loop for webhook retries; run it with an admin-scoped API key that has `admin:write`, and use `--once` or `--max-iterations N` for cron jobs, smoke tests, and bounded maintenance runs. Retry output remains value-redacted even when the worker redelivers first-party event metadata.

`notifications retry-due` runs one retry batch over due failed notification deliveries and exits. `workers notification-retry` is the deployable scheduler loop for notification retries; run it with an admin-scoped API key that has `admin:write`, and use `--once` or `--max-iterations N` for cron jobs, smoke tests, and bounded maintenance runs.

`workers retention-enforce` is the deployable scheduler loop for audit-log, browser-automation artifact, and governed export-package retention through `/api/v1/governance/retention/enforce`. Run it with an admin-scoped API key that has `admin:write`; use `--once` for cron jobs or smoke tests, or set `--interval-ms` and `--max-iterations` for a bounded loop. Enforcement deletes stale registered screenshot/trace objects only from terminal browser-task jobs, removes expired governed export-package objects from the configured object store, prunes package registry metadata, removes browser artifact metadata from job payloads, and returns aggregate counts without object-store keys or package content.

Run it with an admin-scoped API key that has `admin:write`; use `--once` from CronJobs or smoke tests, or set `--interval-ms` and `--max-iterations` for bounded loops. Agent create/update/import requests can include `safetySettings.promptInjectionGuard` with `{ "mode": "block", "scanUserInput": true, "scanRetrievedContext": true }`. The guard is stored on the agent draft and copied into published versions. At run start, Romeo blocks matching user prompts before messages are persisted; during RAG assembly, matching retrieved chunks are omitted from the provider prompt and the `retrieval.completed` run event records only skipped count and stable category codes. The guard does not return flagged prompt text, chunk text, source content, or detector patterns.

Eval suites support deterministic rubric checks in addition to `expectedContains`: `mustContain`, `mustNotContain`, `minLength`, `maxLength`, `expectedToolCalls`, `expectedToolOutcomes`, and `requiredCitations`. Runs persist structured check details and score partial credit across all configured checks, while the promotion gate still requires every case in the latest run to pass. Tool-call checks read fenced `romeo-tool-call`, `tool-call`, or `json` blocks containing objects such as `{"name":"search","arguments":{"query":"Romeo"}}`; the CLI `--expected-tool` flag creates name-only expectations, while the SDK/API can include primitive argument expectations. Tool-outcome checks read fenced `romeo-tool-outcome`, `tool-outcome`, `tool-result`, or `json` blocks containing metadata-only objects such as `{"name":"search","status":"success","outputKeys":["results"]}` or `{"name":"write_issue","status":"failure","errorCode":"tool_approval_rejected"}`. Outcome checks match tool name plus optional success/failure status, expected output-key subset, and stable error code; raw tool result bodies are not part of the rubric contract. Citation checks read bounded inline `[source:chunk_id]` or `[citation:chunk_id]` markers and Romeo citation-list lines such as `- [1] title (chunk_id)`; `--required-citation` sends exact citation IDs to match.

Tool connector auth checks are available through `/api/v1/tool-connectors/{connectorId}/auth/check`, `client.tool.checkConnectorAuth(...)`, and `romeo tools auth-check`. Checks report only configured/available status, secret scheme, and failure code; they do not return or audit raw secret references or values. The default resolver is disabled; `SECRET_RESOLVER_DRIVER=env` enables self-hosted `env://VARIABLE_NAME` checks, `vault` enables Vault KV-v2 checks, and `aws-sm`, `gcp-sm`, `azure-kv`, or `cloud` enable cloud secret-manager checks. Value resolution is restricted to execution paths such as S3 request signing and imported operation dispatch, and is not exposed through auth-check responses. OpenAPI imports capture safe `apiKey` security-scheme hints for header or query placement and safe OAuth `clientCredentials` hints for token URL plus scope names. `client.tool.updateConnectorAuth(...)` can also send `apiKeyIn`/`apiKeyName` or `oauthTokenUrl`/`oauthScopes`/`oauthClientAuthMethod` explicitly; OAuth client credentials must be stored behind a managed secret ref as JSON with `clientId` and `clientSecret`.

Tool connector activation is available through `PATCH /api/v1/tool-connectors/{connectorId}`, `PATCH /api/v1/tool-connectors/{connectorId}/operations/{operationId}`, `client.tool.updateConnector(...)`, `client.tool.updateOperation(...)`, and the matching `romeo tools connector-enable|connector-disable|operation-enable|operation-disable` commands. Imported connectors and operations still default to disabled. Operation test previews from `/api/v1/tool-connectors/{connectorId}/operations/{operationId}/test` and `client.tool.testOperation(...)` return typed readiness blockers without raw request values; an allowlist configured through the connector network policy is no longer reported as missing, `base_url_missing` blocks specs without a sanitized absolute OpenAPI server URL, and `external_execution_disabled` remains present unless `TOOL_OPERATION_EXECUTION_DRIVER=http-fetch` is explicitly configured. With that driver set and all activation/auth/network gates satisfied, the preview reports `external_worker` plus `ready_for_worker`.

Imported operation dispatch is available through `POST /api/v1/tool-connectors/{connectorId}/operations/{operationId}/dispatch`, `client.tool.dispatchOperation(...)`, and `romeo tools operation-dispatch --connector ID --operation ID --param key=value`. Dispatch performs one bounded outbound request only after the same readiness gates pass. `POST /api/v1/tool-connectors/{connectorId}/operations/{operationId}/dispatch-requests`, `client.tool.enqueueDispatchOperation(...)`, and `romeo tools operation-enqueue` create a queued `tool.operation.dispatch_request` for an external worker without performing network execution. By default the queued job stores connector/operation IDs, method/path template, target host, request key names, approval metadata, `external_tool_operations`, and `external_worker_secret_store_required` only; MCP jobs can also include metadata-only transport hints so the worker can build the MCP `tools/call` JSON-RPC envelope from the reviewed manifest. With `TOOL_DISPATCH_PAYLOAD_STORE_DRIVER=object-store`, Romeo stores raw payload/auth refs in encrypted object-store envelopes and exposes only `managed_encrypted_object_store` metadata in normal job, claim, audit, run, and tool-result surfaces. Enqueue accepts an optional `idempotencyKey` / `--idempotency-key`; Romeo stores only a scoped SHA-256 hash, returns the existing job on safe replay, and rejects reuse for a different request key shape. External workers claim queued dispatch requests through `POST /api/v1/tool-operation-dispatch-requests/claim`, `client.tool.claimDispatchRequest(...)`, or `romeo tools dispatch-request-claim`, and renew active leases through `POST /api/v1/tool-operation-dispatch-requests/{jobId}/renew-lease`, `client.tool.renewDispatchRequestLease(...)`, or `romeo tools dispatch-request-renew --job ID`. Claim and renew responses include routing metadata plus sanitized OAuth token policy, MCP transport hints where applicable, and JSON response-schema subsets when an imported operation declares them, so workers can exchange OAuth client credentials, wrap MCP calls, and validate bounded response bytes locally without returning tokens or bodies. A worker holding an active lease for a managed-payload job can explicitly call `POST /api/v1/tool-operation-dispatch-requests/{jobId}/payload` or `client.tool.readDispatchRequestPayload(...)` to retrieve the raw execution payload; another worker or an expired lease receives a 409. External workers then report sanitized completion/failure through `client.tool.completeDispatchRequest(...)`, `client.tool.failDispatchRequest(...)`, `romeo tools dispatch-request-complete`, or `romeo tools dispatch-request-fail`; readback records only status/content-type/byte-count/truncation/schema-validation or a stable error code and rejects replay after the job is no longer claimed by the calling worker. Operators can cancel queued or running requests through `client.tool.cancelDispatchRequest(...)` or `romeo tools dispatch-request-cancel --job ID`; cancellation returns `outcome: "cancelled"` and stores only stable metadata. Operators or scheduled cleanup jobs can expire stale queued or lease-timed-out requests through `client.tool.expireDispatchRequests(...)` or `romeo tools dispatch-requests-expire`; expiry returns sanitized job IDs and reason codes only. Stale requests reclaimed after three worker leases are failed as `worker_attempts_exhausted` with metadata-only `deadLetter` details and a dead-letter alert in `romeo jobs summary`. Approval-gated imported operations first return `tool_operation_approval_required` with a server-issued `approvalRequestId`; the retry must send `approved: true` plus that request ID, or the CLI flags `--approved --approval-request ID`, with the same request key shape. Successful inline dispatch resolves bearer/API-key secrets internally or exchanges OAuth client credentials against an allowlisted token host, then returns response metadata only: status, content type, body byte count, truncation state, and response-schema validation status. Raw idempotency keys, parameters, request body values, response body text, rendered URLs, secret values, OAuth client credentials, and access tokens are not returned or audited outside the explicit lease-guarded payload retrieval path.

Run-scoped tool execution for model-requested tool calls is available through `POST /api/v1/runs/{runId}/tools/{toolId}/execute` and `client.tool.executeForRun(...)`. The API derives the agent from the run, reuses normal tool binding/approval/quota/audit/tool-call/run-event behavior, and accepts `modelToolCallId` for duplicate side-effect protection. Tool-capable provider requests receive only authorization-filtered schemas for enabled, granted agent tools. Provider-requested tool calls surface in run streams as sanitized `tool.requested` events with tool name, argument keys/count, and a provider-call redaction hash. Single or batched non-approval tool calls execute through the same run-scoped service path and resume OpenAI-compatible provider generation with bounded tool result content. Approval-required model tool calls expose the server-issued `approvalRequestId` in sanitized run events and then stop safely until durable approval/resume is completed. Approved tool-call resumes and worker-dispatch readbacks emit metadata-only `run.continuing` events before generation continues. Out-of-process worker dispatch also remains backlog. The replay guard stores only a scoped hash plus metadata-only input key names in `background_jobs`; raw provider call IDs and raw argument values are not returned or persisted in jobs or run events.

`workers tool-dispatch` is the deployable runner for queued dispatch requests. Without `--payload-file`, it claims only `managed_encrypted_object_store` jobs and reads raw execution payloads through `client.tool.readDispatchRequestPayload(...)` after it owns the active lease. With `--payload-file`, the JSON file must be an object keyed by dispatch job ID; each value may contain `parameters`, `body`, string-valued `headers`, and optional worker-local `auth`, allowing legacy external-payload jobs or operator-controlled smoke payloads. Supported worker auth is `{"type":"bearer","secretRef":"env://TOKEN"}`, `{"type":"api_key","secretRef":"vault://tools/api-key","apiKeyIn":"header|query","apiKeyName":"x-api-key"}`, or `{"type":"oauth2_client_credentials","secretRef":"aws-sm://prod/tool-oauth-client"}` when the worker is started with a matching `--secret-resolver env|vault|aws-sm|gcp-sm|azure-kv|cloud`; the default `--secret-resolver disabled` fails auth closed. OAuth secrets must be JSON with `clientId` and `clientSecret`; token URL, scopes, and client auth method come from the claimed job's sanitized connector policy. When the app is configured with `TOOL_DISPATCH_PAYLOAD_STORE_DRIVER=object-store`, enqueue and claim responses report `managed_encrypted_object_store`; claim responses can include `payloadStore` object-key metadata for the encrypted payload envelope, while jobs, audits, run events, and model-visible tool results still expose only request key names and storage posture. For MCP Streamable HTTP jobs, claim responses include only protocol/tool-name/version metadata and the worker wraps raw payload arguments as an MCP `tools/call` JSON-RPC request at fetch time. The worker renders path parameters, sends remaining parameters as query parameters, performs HTTPS requests only, fails closed on redirects, denies local/private literal hosts, DNS-resolved private/link-local/reserved addresses, and Kubernetes service DNS names by default, bounds fetch timeout and response bytes, validates JSON response bodies against sanitized claim-time schemas when present, and completes jobs with response metadata only. Payload files are an optional external-store/local-development path; do not persist them in the app database or general logs.

Approval-gated tool execution is explicitly two-step. A blocked execution returns `tool_approval_required` with `approvalRequestId`; approved execution must send `approved: true` plus that request ID. Pending caller-owned approvals can be listed with `/api/v1/tool-approvals` or `client.tool.approvals(...)`, which returns metadata-only summaries for built-in tool-call approvals and imported operation dispatch approvals with source, tool metadata, risk, approval policy, input key names, connector/operation context, requested time, expiry, and available actions. Caller-owned approvals can be rejected with `POST /api/v1/tool-approvals/{approvalRequestId}/reject` or `client.tool.rejectApproval(...)`. Rejection records metadata-only decision state, removes the approval from the pending queue, terminalizes waiting built-in approval runs with sanitized `tool.failed` and `run.cancelled` events, blocks imported-operation replay before network execution, and prevents later replay approval. Missing, stale, mismatched, rejected, consumed, or cross-run approval IDs fail before quota consumption and are audited without raw tool input.

Production notification adapter readiness is visible through `GET /api/v1/admin/notifications/adapter-live-posture` and `client.admin.notificationAdapterLivePosture()` after reviewed metadata-only evidence is mounted through `NOTIFICATION_ADAPTER_LIVE_EVIDENCE_PATH`.

Workflows are declarative and intentionally constrained. The current safe workflow surface supports product-owned workflow templates, optional interval schedules, model-backed agent-run steps, agent handoff steps, multi-agent room steps, bounded retry policy, fail/continue recovery policy, human approval gates, explicit tool-chain approval gates, approved browser-task gates, and notification ledger steps; it does not execute arbitrary code, in-process pipelines, unaudited tool execution, or in-process browser automation. Agent-run, handoff, and room steps create internal workflow chats, start normal `/api/v1/runs`, and store only chat/run identifiers, source-step IDs, context length, attempt metadata, and status in workflow step output. Handoff steps must reference an earlier agent step and may carry bounded prior assistant text into the receiving agent's chat prompt without copying that text into workflow output or audit metadata. Room steps require 2-5 unique workspace agents, fan out normal linked model runs, and stay in `waiting_run` until every linked run reaches a terminal status; room output stores `agentIds`, `chatIds`, `runIds`, and run statuses only. Tool-chain approval steps stop the workflow with `waiting_approval` and expose only chain name, risk level, approval prompt, and input key names; they do not execute tools or copy raw run-input values. Browser-task steps require HTTPS, non-local, no-query target URLs, stop for approval, expose only target origin/host and sandbox metadata before approval, then queue a metadata-only external-worker job and move to `waiting_run`; only the active worker claim receives the raw task. `retryPolicy.maxAttempts` is capped at 3 total attempts for agent-run and handoff steps; when a linked run is cancelled or failed, `workflows resume` can start the next attempt and records previous run IDs/statuses without prompt or response content. `recoveryPolicy.onFailure` defaults to `fail`; setting it to `continue` marks the failed agent step complete with sanitized recovery metadata and evaluates the next step, so workflows can route into a tool approval or notification escalation without storing raw prompt or output text. Runs stop at agent steps with `waiting_run` until `workflows resume` or the SDK resume method observes the linked model run has completed, stop at browser steps until the browser worker completes/fails/expires the task, and stop at approval steps until `workflows approve` or the SDK approval method is called. `workers workflow-resume` is the deployable scheduler loop for waiting agent-run, handoff, and room steps; it lists visible workflows, resumes bounded `waiting_run` workflow runs, and can be run with `--once` from CronJobs. Kubernetes deployments can start from `deploy/helm/workflow-resume-cronjob.example.yaml`. Notification steps can include a bounded top-level run-input condition such as `{ "inputKey": "route", "equals": "send" }`; non-matching notifications are recorded as skipped without copying the input value or message text into audit metadata. Template instantiation creates normal workflow definitions through the same authorization, agent validation, and audit path as hand-authored workflows. `workflows run-due-schedules` starts due scheduled workflows visible to the caller and advances `nextRunAt`; run it from cron or a worker with `agents:run` and `runs:create` scopes.

Retention enforcement is available through `POST /api/v1/governance/retention/enforce` and `romeo governance retention-enforce`. It deletes audit logs older than the current organization policy cutoff, stale generated voice artifacts from the usage ledger, stale registered browser-automation screenshot/trace objects attached to terminal jobs, and expired governed export-package artifacts tracked by the bounded package registry, then writes a sanitized enforcement audit event containing the cutoff and aggregate deletion counts without object-store keys, artifact bytes, or package content.

Compliance reports are available through `/api/v1/governance/compliance-report`, `/api/v1/governance/compliance-report.csv`, `client.governance.complianceReport(...)`, and the matching CLI commands. Local connector syncs store a cursor with file names, content hashes, and source IDs. Unchanged files are reused on later syncs instead of reindexed; sources created by the prior connector sync and absent from the latest sync are deleted through the normal knowledge-source deletion path, which removes chunks and records storage deletion usage without affecting manually uploaded sources.

The app Data connectors panel surfaces the latest failed sync with a sanitized failure label, error code, and created/reused/deleted counters. It does not render fetched page text, uploaded source text, raw connector config, or secret references.

Website, RSS, GitHub, S3, Confluence, Jira, Notion, Linear, and Slack connector sync is disabled by default. Managed connector creation is also runtime-posture gated: when the catalog reports driver, allowlist, S3 endpoint, or required credential blockers, create calls fail with `409 connector_runtime_not_configured` and stable blocked reason codes instead of persisting a connector that cannot run; local imports remain creatable. `DATA_CONNECTOR_EXECUTION_DRIVER=website-fetch` enables bounded website/RSS fetches, `github-fetch` enables a bounded GitHub API adapter, `s3-fetch` enables the built-in S3 reader, `atlassian-fetch` enables bounded Confluence/Jira adapters, `notion-fetch` enables bounded Notion page/block import, `linear-fetch` enables bounded Linear GraphQL issue import, `slack-fetch` enables bounded Slack channel message import, and `managed-fetch` routes all managed fetch connector types. RSS/Atom feeds are converted to markdown before normal knowledge ingestion. GitHub sync reads repository trees through `api.github.com`, imports supported text files under the configured path prefix, caps file counts and byte sizes, and stores only repository, branch, path prefix, file count, and byte count in sync summaries. It uses connector-specific managed `secretRef` tokens, delegated OAuth `delegatedOAuthConnectionId` tokens, or deployment fallback `DATA_CONNECTOR_GITHUB_TOKEN`; a connector can use only one connector-specific credential source, and no token source is copied into sync summaries or audit records. S3 sync lists bounded objects and reads text-like objects through presigned requests using deployment S3 credentials or connector-specific managed credentials resolved only inside the S3 signing path. Confluence sync uses bounded CQL against `/wiki/rest/api/content/search`; Jira sync uses bounded JQL against `/rest/api/3/search/jql`; both require a value-capable connector `secretRef` and sync summaries return query hashes rather than raw CQL/JQL. Notion sync defaults to `https://api.notion.com`, sends an explicit `Notion-Version`, searches pages through `/v1/search`, reads bounded page block children, requires a value-capable connector `secretRef`, and returns query hashes rather than raw search text. Linear sync defaults to `https://api.linear.app/graphql`, uses a fixed bounded issue query shape with optional local filter text, requires a value-capable connector `secretRef`, and returns query hashes rather than raw filter text. Slack sync defaults to `https://slack.com/api`, reads bounded messages through `conversations.history` for explicit `channelIds`, requires a value-capable connector `secretRef`, and returns channel hashes rather than raw channel IDs. `DATA_CONNECTOR_FETCH_RETRY_ATTEMPTS` and `DATA_CONNECTOR_FETCH_RETRY_BACKOFF_MS` bound managed-fetch retries for 429, 500, 502, 503, 504, and GitHub-style exhausted rate-limit responses; `Retry-After` is honored when supplied, and transient response bodies are not copied into sync summaries or audits. Set `DATA_CONNECTOR_FETCH_ALLOWED_HOSTS` to exact hosts or `*.example.com` suffix rules to enforce website/RSS/Atlassian/Notion/Linear/Slack egress allowlists; blocked hosts fail before network calls. Set `DATA_CONNECTOR_EGRESS_POLICY=require_allowlist` to make website/RSS/Atlassian/Notion/Linear/Slack sync fail closed when the allowlist is empty. Connector create APIs accept `sourceAccessMode`; CLI creation shortcuts currently cover the website/RSS/local flows, while API/SDK callers can create every cataloged connector type. `connector_owner` limits imported sources to the connector creator and admins during source listing, KB query, and agent retrieval, while the default `knowledge_base` mode follows normal KB grants. `connectors create-website` and `connectors create-rss` accept `--sync-interval-minutes`; scheduled connectors set `nextSyncAt`, and `workers data-connector-sync` runs a bounded polling loop for active due non-local connectors. Kubernetes deployments can start from `deploy/helm/data-connector-sync-cronjob.example.yaml`, which runs the worker once per CronJob schedule using a Secret-provided base URL and API key. Admins can read sanitized live connector runtime and worker posture through `GET /api/v1/admin/data-connectors/posture` or `client.admin.dataConnectorPosture()` after mounting reviewed `DATA_CONNECTOR_LIVE_EVIDENCE_PATH`; the report omits allowed hosts, endpoint URLs, connector configs, raw connector content, secret refs, tokens, evidence paths, and evidence bodies.

Prompt templates are available through `/api/v1/prompt-templates`, `/api/v1/prompt-marketplace`, and `/api/v1/prompt-templates/{promptTemplateId}/shares`. `client.collaboration.promptTemplates(...)`, `promptMarketplace(...)`, `createPromptTemplate(...)`, `updatePromptTemplate(...)`, and `sharePromptTemplate(...)` use the same resource-grant model as other shared resources. The CLI supports `romeo prompts list`, `romeo prompts marketplace`, `romeo prompts create`, `romeo prompts update`, and `romeo share prompt`. Private prompts are visible only to the owner or explicit grants, workspace/marketplace prompts are discoverable inside the authorized workspace, and audit metadata records IDs, visibility, tag counts, and changed fields rather than prompt bodies.

Billing plan hooks are intentionally provider-neutral. `GET /api/v1/billing/plan`, `client.admin.billingPlan()`, and `romeo billing plan` read the current organization plan. `POST /api/v1/billing/plan`, `client.admin.applyBillingPlan(...)`, and `romeo billing apply-plan --code team --name Team --quota run.started:1000:monthly,tool.call:5000:monthly` upsert the plan and apply org-level quota buckets from templates. `POST /api/v1/billing/external-events`, `client.admin.syncExternalBillingEvent(...)`, and `romeo billing sync-external` accept sanitized customer/subscription/invoice lifecycle fields and fold them into the current billing plan without storing raw provider payloads. `POST /api/v1/billing/webhooks/stripe` is the Stripe provider-facing webhook endpoint; it requires a valid Stripe HMAC timestamp signature from `BILLING_STRIPE_WEBHOOK_SECRET`. `POST /api/v1/billing/webhooks/generic` is for billing proxies and requires `x-romeo-billing-timestamp` plus `x-romeo-billing-signature` from `BILLING_GENERIC_WEBHOOK_SECRET`. Both signed webhook paths map into the same sanitized lifecycle shape and write normal billing audits under a disabled per-org `system_billing_webhook` actor so the Postgres audit foreign-key contract remains valid. Billing enforcement still happens through Romeo quota buckets.

Billing entitlement readback is available through `GET /api/v1/billing/entitlements`, `client.admin.billingEntitlements()`, and `romeo billing entitlements`. It compares the current billing plan quota templates to enforced org quota buckets, reports missing or mismatched quota limits/reset intervals, billing statuses that are not entitled, unmanaged org quota counts, and sanitized external customer/subscription presence only. `POST /api/v1/billing/entitlements/reconcile`, `client.admin.reconcileBillingEntitlements()`, and `romeo billing reconcile-entitlements` idempotently recreate missing org quota buckets and repair mismatched limits/reset intervals from the current plan while writing metadata-only audit counts. It does not store raw billing-provider payloads and does not delete extra manually configured quota buckets. Use `romeo workers billing-entitlement-reconcile --once` for scheduled one-shot execution.

Billing lifecycle posture is available through `GET /api/v1/billing/lifecycle`, `client.admin.billingLifecycle()`, and `romeo billing lifecycle`. Apply or sync billing plans with a bounded `lifecycle` object containing ISO timestamps such as `trialEndsAt`, `currentPeriodEndsAt`, `pastDueGraceEndsAt`, and `cancelAt`; Romeo stores those as sanitized plan metadata. `POST /api/v1/billing/lifecycle/enforce`, `client.admin.enforceBillingLifecycle()`, and `romeo billing enforce-lifecycle` mark expired trials or stale subscription periods as `past_due`, and mark reached cancellation or expired past-due grace deadlines as `canceled`. Enforcement writes metadata-only audit rows and does not store raw provider payloads.

Billing operations posture is available through `GET /api/v1/admin/billing/operations-posture` and `client.admin.billingOperationsPosture()`. Operators generate reviewed metadata-only evidence with `pnpm evidence:billing-operations` after checking entitlement/lifecycle worker cadence, API readback, billing alerting, and worker-log redaction, then mount it through `BILLING_OPERATIONS_EVIDENCE_PATH`. The report returns status, required-check coverage, cadence counts, worker summaries, API readback, alerting, warning codes, and redaction booleans only; it omits mounted paths, evidence bodies, raw billing provider payloads, worker logs, API keys, customer identifiers, alert payloads, and secret values.

Quota buckets are managed through `client.admin.quotas()`, `client.admin.createQuota(...)`, `client.admin.updateQuota(...)`, and `client.admin.deleteQuota(...)`. Distributed quota coordination posture is available through `GET /api/v1/quotas/distributed-status` and `client.admin.quotaCoordinationStatus()`. The report includes driver, enabled/configured/healthy state, key prefix, fail-closed posture, and a stable status code without returning `VALKEY_URL`, credentials, raw tenant identifiers, or quota counter keys. Enable coordination with `QUOTA_COORDINATION_DRIVER=valkey` for multi-replica deployments; the default disabled driver keeps single-node Compose behavior simple. HTTP request rate limiting is configured separately with `HTTP_RATE_LIMIT_DRIVER`, `HTTP_RATE_LIMIT_KEY_PREFIX`, `HTTP_RATE_LIMIT_WINDOW_SECONDS`, `HTTP_RATE_LIMIT_AUTH_MAX`, `HTTP_RATE_LIMIT_PUBLIC_MAX`, `HTTP_RATE_LIMIT_AUTHENTICATED_MAX`, and `HTTP_RATE_LIMIT_WEBHOOK_MAX`; use `HTTP_RATE_LIMIT_DRIVER=valkey` for distributed app-level counters and keep edge/API-gateway limits in front of public SaaS ingress.

For a local release smoke without publishing packages, pack both workspaces, create a throwaway project, and point the CLI dependency at the SDK tarball through the package-manager override mechanism before installing the CLI tarball. With pnpm v11, `tsx` also requires allowing the `esbuild` postinstall build in that throwaway project.

Use `pnpm release:pack` for the standard pre-publish package check. It runs the verifier, packs the TypeScript SDK before the CLI, verifies expected tarball files, rejects test files in artifacts, confirms the packed CLI depends on the same SDK version, and writes `release-manifest.json` with artifact sizes and SHA-256 hashes.

Use `pnpm release:provenance` after channel, security evidence, and SBOM generation to write redacted `romeo.release-provenance.v1` evidence. Use `pnpm release:publish-plan` after that to produce a reviewable publish plan. The plan validates artifact hashes, channel version, optional security evidence, release notes, provenance schema/digest linkage, and signed or attested provenance requirements when enabled, then emits explicit commands for registry publication, signed Git tagging, tag push, and release-note/asset publication. It does not perform network writes unless a CI job deliberately executes the generated commands with registry and repository credentials.
