# Remaining Work Execution Backlog

This folder turns the remaining PRD findings into execution-ready backlog items. The phase track files still describe the product strategy and scope; these execution files define the concrete work packets, acceptance evidence, and validation gates that determine whether Romeo is full-product complete.

## Backlog Rules

- Keep Docker Compose and Kubernetes compatibility in every ticket.
- Keep CloudNativePG and external hosted Postgres on the same application contract: `DATABASE_URL`, migration command, schema validator, backup, restore, object-store configuration, and DR drill.
- The Phase 19 greenfield database migration is accepted and locked. Do not add corrective migration chains; future schema changes need forward-only migrations with upgrade tests and rollback or mitigation notes.
- Keep implementation split by domain and responsibility. Do not introduce broad catch-all repositories, services, workers, or deployment scripts.
- Treat secrets, raw prompts, provider payloads, connector payloads, worker payloads, and webhook bodies as sensitive by default. Evidence must prove they are absent from logs, audits, jobs, usage records, sync summaries, and support bundles unless a retention policy explicitly allows otherwise.

## Ticket Format

Each backlog item uses the same fields:

- Phase and dependency.
- Goal.
- Scope details.
- Tasks.
- Definition of done.
- Testing.
- Validation and evidence.
- Compose and Kubernetes impact.
- Security and migration notes.

## Evidence Storage

Evidence should be generated by scripts where possible and stored as release artifacts or CI artifacts. Use stable names such as:

- `postgres-schema-validation.json`
- `postgres-conformance.json`
- `compose-smoke.json`
- `compose-workers-smoke.json`
- `compose-backup-restore-smoke.json`
- `kubernetes-live-smoke.json`
- `kubernetes-external-postgres-smoke.json`
- `kubernetes-cloudnativepg-smoke.json`
- `kubernetes-dr-drill.json`
- `release-manifest.json`
- `security-evidence.json`
- `scale-results.json`
- `ga-checklist.json`

Evidence must be redacted before it is attached to release notes, support bundles, tickets, or shared documentation.

Generate the draft GA checklist with `pnpm ga:checklist -- --output dist/release/ga-checklist.json`. Use `--strict` only for promotion gates once target-tier live evidence and approved exception files are present.
