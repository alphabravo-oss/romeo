# Tool Safety

Romeo supports extensibility without arbitrary in-process plugin execution.

Every tool declares:

- risk level
- required scopes
- parameter schema
- output schema
- timeout
- approval policy
- audit policy
- allowed agents
- allowed groups

Connector credentials must be attached as managed secret references, not raw values. Accepted reference schemes are `vault://`, `external-secret://`, `aws-sm://`, `gcp-sm://`, `azure-kv://`, and opt-in self-hosted `env://VARIABLE_NAME`; execution code must resolve those references through an isolated secret provider before any external call is enabled. Auth availability checks may report only configured state, availability, secret scheme, and failure code; they must not return or audit raw references or secret values.

`SECRET_RESOLVER_DRIVER=disabled` is the default. `SECRET_RESOLVER_DRIVER=env` enables availability checks for `env://VARIABLE_NAME` references and permits S3 connector credentials to be resolved internally for request signing when the env value is JSON with `accessKeyId` and `secretAccessKey`. `SECRET_RESOLVER_DRIVER=vault` enables Vault KV-v2 metadata checks and execution-only value resolution for `vault://path`. `SECRET_RESOLVER_DRIVER=aws-sm`, `gcp-sm`, and `azure-kv` enable provider-specific metadata checks and execution-only value resolution for AWS Secrets Manager, GCP Secret Manager, and Azure Key Vault; `SECRET_RESOLVER_DRIVER=cloud` routes all three cloud schemes. Romeo does not return secret values or copy them into audit metadata. Use External Secrets, workload identity, or platform secret injection rather than committing credentials.

Imported connector operation tests are readiness previews only. Disabled reasons are typed as `connector_disabled`, `operation_disabled`, `base_url_missing`, `auth_not_configured`, `network_policy_missing`, or `external_execution_disabled`; configured allowlists are not reported as missing, and raw parameter/body values are not returned or audited. The preview also returns a sanitized worker execution plan with dispatch state, queue name, approval requirement, secret-reference scheme, network-policy counts, and remaining blockers. `TOOL_OPERATION_EXECUTION_DRIVER=disabled` is the default and keeps `external_execution_disabled` present. `TOOL_OPERATION_EXECUTION_DRIVER=http-fetch` only changes the plan to `external_worker` and `ready_for_worker` after the imported connector, operation, sanitized OpenAPI base URL, auth state, and network allowlist are all configured through the public admin surfaces.

Imported connector dispatch is available through the separate operation dispatch endpoint and CLI command. It reuses the same fail-closed readiness gates, enforces the connector host allowlist, injects bearer auth, API-key auth, or OAuth client-credentials bearer auth from the configured secret resolver, and bounds outbound fetches with `TOOL_OPERATION_FETCH_TIMEOUT_MS` plus `TOOL_OPERATION_FETCH_MAX_BYTES`. The dispatch-request endpoint and `romeo tools operation-enqueue` use the same gates and approval flow but queue a `tool.operation.dispatch_request` for an external worker instead of making a network call; by default the queued job stores only connector/operation IDs, method/path template, host, request key names, approval metadata, queue name, optional idempotency-key hash, and `external_worker_secret_store_required`. When `TOOL_DISPATCH_PAYLOAD_STORE_DRIVER=object-store` is enabled with a high-entropy `TOOL_DISPATCH_PAYLOAD_ENCRYPTION_KEY`, Romeo writes raw operation payloads and worker auth refs to AES-GCM encrypted object-store envelopes before queueing, stores only `managed_encrypted_object_store` plus object-key metadata in job payloads and claim responses, and best-effort deletes those objects after complete/fail/cancel/expiry/dead-letter terminal transitions. Raw payload values and raw idempotency keys must stay out of Romeo jobs and audit logs. External workers must claim a dispatch request through `POST /api/v1/tool-operation-dispatch-requests/claim`, `client.tool.claimDispatchRequest(...)`, or `romeo tools dispatch-request-claim` before executing it, and may renew the active lease with `POST /api/v1/tool-operation-dispatch-requests/{jobId}/renew-lease`, `client.tool.renewDispatchRequestLease(...)`, or `romeo tools dispatch-request-renew`. Claim responses expose routing metadata, request key names, lease timestamps, sanitized OAuth client-credentials token policy when configured, optional managed encrypted payload object references, and sanitized JSON response-schema subsets for worker-side validation. Completion/failure readback accepts only sanitized metadata from the worker that holds an active lease, records a terminal job state, audits status/content-type/byte-count/truncation/schema-validation or stable error code, and rejects replay after the job is no longer claimed by that worker. Operators can cancel queued or running dispatch requests through `POST /api/v1/tool-operation-dispatch-requests/{jobId}/cancel`, `client.tool.cancelDispatchRequest(...)`, or `romeo tools dispatch-request-cancel`; cancellation stores only `worker_cancelled`, a stable reason code, actor ID, and timestamps. Operators or scheduled cleanup jobs can expire stale queued or lease-timed-out dispatch requests through `POST /api/v1/tool-operation-dispatch-requests/expire`, `client.tool.expireDispatchRequests(...)`, or `romeo tools dispatch-requests-expire`; expiry stores only `worker_dispatch_request_expired`, stable reason metadata, actor ID, and timestamps. A stale dispatch request reclaimed after three worker leases is failed as `worker_attempts_exhausted` with metadata-only `deadLetter` details and a job-summary dead-letter alert. API-key auth uses a safe OpenAPI `apiKey` security-scheme hint when present, supporting header and query placement, and otherwise defaults to the `x-api-key` header. OAuth client-credentials auth uses a safe imported or explicit token URL, scope names only, and a managed secret JSON object with `clientId` and `clientSecret`; the token host must also be allowlisted, token responses are bounded, and access tokens are never returned or audited. Imported operations whose approval policy is not `never` use a two-step flow: the first dispatch attempt returns a server-issued `approvalRequestId` backed by metadata-only approval-request job state, and the approved retry must include `approved: true` plus that request ID with the same request key shape before network execution or queueing. Dispatch results return job IDs, request key names, host, status, content type, byte count, truncation state, and response-schema validation status only; they do not return response bodies, rendered URLs, raw idempotency keys, raw parameters, raw body values, secret references, secret values, OAuth client credentials, or access tokens.

`romeo workers tool-dispatch` is the first deployable runner for queued dispatch requests. With no payload file configured it claims only `managed_encrypted_object_store` jobs and reads raw parameters/body/auth refs through the lease-guarded `POST /api/v1/tool-operation-dispatch-requests/{jobId}/payload` API; that endpoint requires the active worker lease and records metadata-only payload-read audit entries. With an external payload file keyed by dispatch job ID, the worker can also resolve legacy or operator-supplied `external_worker_secret_store_required` jobs. Auth secret values are resolved only in the worker when `--secret-resolver env|vault|aws-sm|gcp-sm|azure-kv|cloud` or the matching `TOOL_DISPATCH_SECRET_RESOLVER_DRIVER` value is set; the default disabled resolver fails auth closed. Vault refs use KV-v2 `vault://path`, cloud refs use `aws-sm://`, `gcp-sm://`, or `azure-kv://`, and the `cloud` driver routes all three cloud schemes. For OAuth, the payload supplies only the managed secret ref, while the token URL, scopes, and client-auth method come from sanitized claim metadata. MCP Streamable HTTP claims add only metadata-only transport hints; the worker constructs the MCP `tools/call` JSON-RPC envelope from those hints and the raw payload arguments at execution time. Live MCP readiness evidence must prove the protocol headers, JSON-RPC envelope, nonzero call count, and payload/output redaction without retaining raw arguments. The worker executes HTTPS requests only, fails closed on redirects, denies local/private literal hosts, DNS-resolved private/link-local/reserved addresses, and Kubernetes service DNS names by default, bounds timeout and response bytes, validates JSON responses against sanitized claim-time schemas when available, and reports only sanitized response metadata or stable worker error codes. Live NetworkPolicy/CNI egress enforcement and pod log-redaction evidence remain required before imported tools are considered fully production-ready.

Milestone 1 built-ins:

- calculator
- date/time

Approval-gated tools use a two-step API flow. The first execution attempt records an `approval_required` tool-call trace and returns a server-issued `approvalRequestId`. The approved execution must include both `approved: true` and that request ID; direct `approved: true` calls without a matching request are rejected and audited as blocked attempts.

Forbidden by default:

- user-uploaded arbitrary Python
- Open WebUI-style pipelines
- in-process untrusted plugins
- shell execution without strict sandboxing and admin enablement
