# Kubernetes Deployment

The Helm chart now renders the core production surface: app Deployment/Service/HPA, migration Job, ConfigMap/Secret wiring, ServiceAccounts, PodDisruptionBudget, optional Ingress, optional NetworkPolicy, worker CronJobs, and Postgres backup CronJob.

Production guidance:

- CloudNativePG-managed Postgres or external hosted Postgres
- external Valkey
- S3-compatible object storage
- External Secrets Operator
- cert-manager-managed TLS
- OIDC/Keycloak configured through secrets
- OpenTelemetry collector endpoint

The app must not assume Kubernetes for self-hosted local operation.

For private or disconnected environments, use [Private and Air-Gapped Deployment](./air-gapped-deployment.md) with the Helm values in this directory.

The full-product backlog tracks Kubernetes production hardening in [Romeo Full-Product Completion Backlog](./full-product-backlog.md). The enterprise Postgres contract should support both CloudNativePG-managed clusters and externally hosted Postgres from the start: the application should consume the same `DATABASE_URL`, migration job, pgvector readiness, backup/restore, and DR drill interfaces in both modes.

Kubernetes values must keep `REPOSITORY_DRIVER=postgres`. The process-local memory repository is only for development and is rejected when `DEV_SEEDED_LOGIN=false`, which is also the Helm default. External Postgres and CloudNativePG modes should therefore differ only in how `DATABASE_URL` and database operations credentials are supplied, not in application behavior. For externally hosted Postgres, the Secret-provided `DATABASE_URL` should use provider TLS and preferably `sslmode=verify-full`; readiness and Postgres operational posture report sanitized warning codes for remote URLs without required TLS or certificate verification without returning the database host, user, password, or URL.

The chart sets `HOME`, `XDG_CACHE_HOME`, `COREPACK_HOME`, and `PNPM_HOME` to writable `/tmp` paths for app, migration, backup, and worker containers. Keep those env vars in place when hardening pod security: migration jobs and workers invoke `pnpm` through Corepack, and restricted non-root pods must not try to write Corepack cache data under `/`.

Render and lint the chart before applying it:

```sh
helm lint deploy/helm
pnpm smoke:kubernetes:render
helm template romeo deploy/helm \
  -f deploy/helm/external-postgres-values.example.yaml \
  --namespace romeo
helm template romeo deploy/helm \
  -f deploy/helm/cloudnativepg-values.example.yaml \
  --namespace romeo
```

The chart includes `deploy/helm/values.schema.json`, so Helm rejects unsupported values such as an unknown `postgres.mode` before rendering. Treat schema failures as configuration defects rather than runtime warnings.

`pnpm smoke:kubernetes:render` is the offline chart-contract gate. It renders default, external Postgres, CloudNativePG, and enterprise-surface variants, then checks that sensitive values stay behind Secret references, app and migration resources use the shared `DATABASE_URL` contract, worker CronJobs are bounded and scoped, probes/resources/security contexts are present, NetworkPolicy/Ingress render correctly, and app HPA output targets the Deployment. It does not replace live namespace smoke, pod-log scanning, or DR evidence.

```sh
export KUBERNETES_NETWORKPOLICY_CONFIRM_CNI_ENFORCEMENT=true

  --output dist/ci/kubernetes-networkpolicy-smoke.json
```

`pnpm smoke:kubernetes:networkpolicy` creates an ephemeral namespace with an app-labeled client pod and two restricted HTTP server pods. It proves both endpoints are reachable before a policy is applied, applies an egress-only `networking.k8s.io/v1` NetworkPolicy using the same app labels as the Romeo chart, then requires the allowed endpoint to remain reachable and the denied endpoint to fail. This proves live CNI enforcement for the policy pattern that `pnpm smoke:kubernetes:render` verifies in Helm output. Use internally mirrored, digest-pinned probe images in regulated clusters. `pnpm ga:target-preflight` checks `kubectl` reachability, the `networking.k8s.io` API, explicit CNI-enforcement confirmation, digest-pinned probe image posture, and bounded propagation timing before reporting this gate ready. Use `--dry-run --output dist/ci/kubernetes-networkpolicy-plan.json` only for planning evidence; dry-run output does not prove enforcement.

When the active context is a disposable `kind-*` cluster and the harness builds the app image locally, it loads that image into the kind cluster before Helm install and records metadata-only `localImageLoadedToKind` posture. This harness does not replace CloudNativePG operator validation, external hosted Postgres staging validation, real IdP login validation, or combined database/object-store DR drills.

When those Kubernetes evidence files are mounted through `evidenceMount`, `GET /api/v1/admin/kubernetes/posture` validates the same GA-facing metadata shape before reporting ready. `pnpm smoke:kubernetes:dr` is the live database/object-store DR harness for the two GA database modes. In external Postgres mode it creates disposable source and restore namespaces with smoke-owned pgvector, Valkey, and RustFS dependencies, installs Romeo, writes representative API records and stored artifacts, runs Postgres and object-store backup Jobs through the shared maintenance scripts, copies backup artifacts through a Kubernetes PVC, restores into an isolated namespace, validates the restored schema, starts Romeo with seeded login disabled, and reads restored chats, knowledge records, workflow records, and attachment bytes through the API. CloudNativePG mode uses the same backup/restore/readback sequence but requires operator-managed source and restore connection Secrets in explicit namespaces. Prefer a reviewed `romeo.kubernetes-dr-plan.v1` file for both modes so `pnpm ga:target-preflight` and the live smoke agree on namespaces, release names, image, and CloudNativePG Secret refs:

```sh
export KUBERNETES_DR_PLAN_FILE=dist/ci/kubernetes-dr-plan.json
export KUBERNETES_DR_SKIP_BUILD=true
export KUBERNETES_DR_APP_IMAGE="registry.example/romeo/app:1.2.3@sha256:<digest>"

pnpm smoke:kubernetes:dr \
  --mode external-postgres \
  --dr-plan-file "$KUBERNETES_DR_PLAN_FILE" \
  --skip-build \
  --image "$KUBERNETES_DR_APP_IMAGE" \
  --output dist/ci/kubernetes-external-postgres-dr.json

pnpm smoke:kubernetes:dr \
  --mode cloudnativepg \
  --dr-plan-file "$KUBERNETES_DR_PLAN_FILE" \
  --skip-build \
  --image "$KUBERNETES_DR_APP_IMAGE" \
  --output dist/ci/kubernetes-cloudnativepg-dr.json
```

The plan must include `modes.external-postgres` and `modes.cloudnativepg`, each with distinct `sourceNamespace` and `restoreNamespace`; CloudNativePG mode must also include `sourceDatabaseUrlSecret` and `restoreDatabaseUrlSecret` in `name:key` format. `pnpm ga:target-preflight` validates the plan shape, requires `KUBERNETES_DR_SKIP_BUILD=true` plus a reviewed digest-pinned `KUBERNETES_DR_APP_IMAGE`, and checks CloudNativePG Secret presence with `kubectl get secret` while returning only counts and booleans, never image refs, Secret names, keys, values, database URLs, or plan bodies. The target preflight path does not require Docker on the evidence-collection host. Dry-run mode is planning evidence only and is rejected by `pnpm ga:checklist`; GA requires live `status=passed` evidence with source and restore pod-log scan counts plus generated-secret and raw-content sentinel redaction proof. Use dedicated DR namespaces and isolated restore databases because the restore jobs are intentionally destructive after explicit confirmation guards.

`postgres.mode=external` expects `postgres.databaseUrlSecret.name` and `key` to point at a Secret containing `DATABASE_URL`. `postgres.mode=cloudnativepg` expects `postgres.cloudnativepg.databaseUrlSecret.name` and `key` to point at the CloudNativePG-managed app connection Secret. The chart does not install CloudNativePG or create a database cluster; this keeps the Romeo chart compatible with operator-managed clusters and externally hosted Postgres. External hosted Postgres Secrets should include the provider-required TLS query parameters, preferably `sslmode=verify-full`; if the selected provider only supports encrypted transport without hostname verification, record that exception in release evidence and expect `postgres_connection_security_warning` until stronger verification is available.

CloudNativePG examples live under `deploy/cloudnativepg`. They define an operator-owned `romeo-pg` cluster, Barman Cloud plugin object-store backup target, scheduled and on-demand backups, and an isolated `romeo-pg-restore` recovery cluster. The default values in `deploy/helm/cloudnativepg-values.example.yaml` consume the CloudNativePG-generated `romeo-pg-app` Secret key `uri` and expose it to the app as `DATABASE_URL`. If an External Secrets layer projects that URI into a different key, update `postgres.cloudnativepg.databaseUrlSecret.key` accordingly.

Runtime secrets should come from `secrets.existingSecret` or External Secrets. At minimum, that Secret should provide `SESSION_SECRET`, `LOCAL_AUTH_SECRET_ENCRYPTION_KEY`, `WEBHOOK_SIGNING_KEY`, S3 credentials when `OBJECT_STORE_DRIVER=s3`, delegated OAuth client secrets and token encryption keys when delegated OAuth is enabled, `MANAGED_SECRET_ENCRYPTION_KEY` when admins will use `romeo-secret://` locally managed refs, `VAULT_*` values when Vault-backed managed-secret ingestion or Vault ref resolution is enabled, and provider credentials for any enabled integrations. `LOCAL_AUTH_SECRET_ENCRYPTION_KEY` protects encrypted local MFA factors, and `MANAGED_SECRET_ENCRYPTION_KEY` protects encrypted local managed-secret envelopes created through `/api/v1/admin/secrets`; both should be at least 32 high-entropy characters. `LOCAL_AUTH_SECRET_ENCRYPTION_KEY_PREVIOUS` and `MANAGED_SECRET_ENCRYPTION_KEY_PREVIOUS` should be empty except during a staged rewrap window. Use [Secret Rotation Runbook](./secret-rotation.md) for staged OIDC PKCE rotation with `SESSION_SECRET_PREVIOUS`, encrypted MFA/managed-secret envelope rewrap, coordinated webhook signing-key cutover, and acceptable evidence. Worker CronJobs use `workers.apiKeySecret` for `ROMEO_API_KEY`; use a scoped service-account key rather than a personal admin key.

Native file storage uses the same S3-compatible object-store values as chat attachments, browser artifacts, voice artifacts, backups, and managed encrypted tool payloads. Bounded inline `POST /api/v1/files` writes allowlisted bytes through the object-store adapter after MIME signature validation, while `POST /api/v1/files/uploads` creates `status=uploading` metadata and returns a short-lived PUT URL for direct object-store upload. `POST /api/v1/files/uploads/resumable` creates a backend-composed resumable session with short-lived PUT URLs for bounded parts; completion reads the staged parts through the object-store adapter, verifies part sizes plus final size/SHA-256/MIME signature, writes the final object, deletes staged parts, and then marks metadata readable. `GET/POST /api/v1/files/{fileId}/shares` manages read/write file grants, and `GET /api/v1/files/{fileId}/content` streams bytes only after org/workspace/resource-grant authorization. Chat image attachments also require PNG/JPEG/GIF/WebP bytes matching the declared MIME signature before object-store persistence. File metadata surfaces server-issued content URLs, never raw object keys, bucket URLs, or secret refs. Treat direct-upload and part-upload URLs as transient secrets in ingress/proxy/app logs. Kubernetes deployments do not need an additional Secret, ConfigMap, service, or migration file for the file API beyond the existing object-store and database contracts.

The migration Job runs `pnpm migrate:postgres`, the same command used by Compose. It is rendered as a pre-install/pre-upgrade Helm hook by default. Run `pnpm validate:postgres` against the same `DATABASE_URL` after the hook succeeds and before production traffic cutover.

Enable worker CronJobs explicitly through `workers.*.enabled`. The chart can render connector sync, workflow resume, webhook retry, notification retry, retention enforcement, billing entitlement reconciliation, billing lifecycle enforcement, tool dispatch, knowledge extraction, voice catalog sync, and Postgres backup jobs. Each worker has its own schedule, resources, service account, and bounded command arguments.

Set `autoscaling.enabled=true` to render an `autoscaling/v2` HorizontalPodAutoscaler for the app Deployment. Configure `autoscaling.minReplicas`, `autoscaling.maxReplicas`, `autoscaling.targetCPUUtilizationPercentage`, and `autoscaling.targetMemoryUtilizationPercentage` according to the deployment tier and database connection budget. When HPA is enabled, the Deployment omits a fixed replica count and the HPA owns app replica selection.

Use [Romeo Deployment Sizing](./deployment-sizing.md) before changing app replicas, HPA bounds, `POSTGRES_POOL_MAX`, worker limits, or KEDA replica caps. `POSTGRES_POOL_MAX` defaults to `10` and caps each app process database pool; the app replica maximum multiplied by that value must fit inside the database's usable connection budget after provider, maintenance-job, admin, and scaler headroom.

`MODEL_PROVIDER_STREAM_TIMEOUT_MS` defaults to `60000` in Helm values and bounds idle model-provider streams. Active streams reset the timer on each chunk; stalled providers fail with a metadata-only `provider_stream_timeout` event. Helm values also expose `MODEL_PROVIDER_RETRY_ATTEMPTS` defaulting to `1`, `MODEL_PROVIDER_RETRY_BACKOFF_MS` defaulting to `250`, `MODEL_PROVIDER_CIRCUIT_FAILURE_THRESHOLD` defaulting to `5`, `MODEL_PROVIDER_CIRCUIT_COOLDOWN_MS` defaulting to `60000`, `MODEL_PROVIDER_DISABLED_IDS` defaulting to empty, and `MODEL_PROVIDER_FALLBACK_MODEL_ID` defaulting to empty. Romeo retries only pre-output stream failures/timeouts, avoids retrying after assistant content has emitted, and fails fast with `provider_circuit_open` once the circuit threshold is reached. Fallback routing uses the configured fallback model only before assistant content is emitted, and kill-switched primary providers are not called when a valid fallback exists. Tune these with provider latency, provider quotas, alerts, live outage drills, and tenant-facing timeout policy before production traffic.

The execution report writes redacted `romeo.ga-target-execution.v1` with command hashes, exit status, timing, skip reasons, env-file metadata counts, and explicit proof that command text, command output, env-file values, and env-file bodies were not stored; gate-specific evidence files from the executed commands still have to pass `pnpm ga:checklist`. For Kubernetes DR, set `KUBERNETES_DR_PLAN_FILE` before running preflight so the suggested command runs both `external-postgres` and `cloudnativepg` with the same reviewed plan. For release readback, set `RELEASE_READBACK_PLAN_FILE` before running preflight so the suggested command collects and validates the same package/image/chart/asset targets that the GA validator requires. For CI governance live evidence, set `CI_GOVERNANCE_EVIDENCE_REVIEWED=true`, `GITHUB_REPOSITORY`, one of `GITHUB_TOKEN` or `GH_TOKEN`, and one of `GITHUB_CI_RUN_ID` or `GITHUB_CI_HEAD_SHA`; preflight returns only configured/valid booleans and redaction proof, not repository slugs, run IDs, branch names, raw GitHub responses, job logs, run URLs, or token values. For target-quality capture, set `TARGET_QUALITY_AGENT_IDS` and `TARGET_QUALITY_REPLAY_FILE` before running preflight so the suggested command includes `--require-eval-passed` and the representative replay fixture that the GA validator requires. For Postgres operations, set `DATABASE_URL`, `POSTGRES_OPERATIONAL_TARGET_TIER=small|enterprise`, `POSTGRES_OPERATIONAL_MODE=cloudnativepg|external-hosted-postgres`, `POSTGRES_TELEMETRY_WINDOW_MINUTES`, `POSTGRES_SLOW_QUERY_THRESHOLD_MS`, `POSTGRES_MAX_BLOCKED_SESSIONS`, `POSTGRES_MAX_DEADLOCKS`, and `POSTGRES_ARCHIVAL_DECISION`; external hosted Postgres strict preflight requires `sslmode=verify-full` on `DATABASE_URL` while returning only booleans and target labels, not the URL or host. For support-bundle live evidence, set `SUPPORT_BUNDLE_EVIDENCE_REVIEWED=true` after generating `dist/ci/support-bundle.json` from the selected metadata-only target evidence set and reviewing redaction evidence. For Qdrant live evidence, set `QDRANT_LIVE_EVIDENCE_REVIEWED=true`, `QDRANT_URL`, `QDRANT_COLLECTION`, `QDRANT_API_KEY`, `VECTOR_NAMESPACE_POLICY`, and `VECTOR_PARTITIONING_POLICY` before running preflight so the suggested command matches the target runtime evidence that will be mounted through `QDRANT_LIVE_EVIDENCE_PATH`. For Qdrant DR, set `QDRANT_DR_RUN_SECRET`, source and restore Qdrant URLs, source and restore collection/API-key env vars, `VECTOR_NAMESPACE_POLICY`, and `VECTOR_PARTITIONING_POLICY` before running preflight so the suggested command emits the three required prepare-source, verify-restore, and cleanup-source smoke calls with explicit `--run-secret`, `--api-key`, `--namespace-policy`, and `--partitioning-policy` arguments. For edge enforcement, set `ROMEO_API_KEY`, `EDGE_ENFORCEMENT_REQUIRE_ADMIN_POSTURE=true`, `EDGE_ENFORCEMENT_REQUIRE_WAF_BLOCK_MODE=true`, body-limit path/byte/status env, rate-limit path/attempt/status env, and WAF probe path/status env before running preflight so the suggested command matches the reviewed ingress/WAF policy. For alert firing, set `ALERT_FIRING_REQUIRED_ALERTS` only when the deployment intentionally replaces the default alert names while retaining provider, queue, and backup coverage. For custom Helm release names, set `ROMEO_NAMESPACE`, `ROMEO_RELEASE_NAME`, `ROMEO_SERVICE_NAME`, and `ROMEO_DEPLOYMENT_NAME` before running preflight; for renamed KEDA resources, set `KEDA_NAMESPACE`, `KEDA_SCALEDJOB_NAME`, and `KEDA_TRIGGERAUTHENTICATION_NAME`. For Qdrant live evidence it validates target URL posture, collection/API-key environment presence, review confirmation, namespace policy, and partitioning policy while returning only safe URL origin, booleans, policy names, and redaction flags. For Qdrant DR it validates configured source/restore URL posture, source/restore collection/API-key environment presence, high-entropy run-secret presence, namespace policy, and partitioning policy while returning only URL origins and boolean configured flags. Preflight, target-plan, target-env-template, and target-execution artifacts are not accepted by `pnpm ga:checklist` as replacement evidence; use them to catch missing prerequisites, order the work, prepare target environment variables, and batch-run ready live smokes, then mount `GA_TARGET_PREFLIGHT_PATH` / `GA_TARGET_PLAN_PATH` / `GA_TARGET_EXECUTION_PATH` only after reviewing that the files are metadata-only.

If operators want the running admin UI/API to display target Postgres operations posture, mount reviewed metadata-only evidence files into the app pod and set `env.POSTGRES_QUERY_PLAN_EVIDENCE_PATH`, `env.POSTGRES_SLOW_QUERY_TELEMETRY_EVIDENCE_PATH`, `env.POSTGRES_LOCK_TELEMETRY_EVIDENCE_PATH`, and `env.POSTGRES_ARCHIVAL_PARTITIONING_DECISION_PATH`. Generate slow-query and lock evidence outside the app process with `pnpm collect:postgres-telemetry -- --slow-output ... --lock-output ...` against the selected target database after `pg_stat_statements` is enabled and representative traffic has run. Generate archival/partitioning decision evidence outside the app process with `pnpm decide:postgres-archival -- --decision ... --accept-decision --output ...` after table-growth, retention, and restore-window review; this command writes metadata evidence only and does not create migrations. Releases that claim target Postgres operations are complete should enable `pnpm ga:checklist -- --require-postgres-operations-live` / `GA_REQUIRE_POSTGRES_OPERATIONS_LIVE=true`, which requires representative query-plan review, slow-query telemetry, lock telemetry, and accepted archival/partitioning evidence. `GET /api/v1/admin/postgres/operational-posture` returns sanitized connection-security posture, evidence status, counts, failure codes, and redaction flags only; it does not return mounted paths, evidence file bodies, database URLs, database hosts, SQL text, query parameter values, row data, lock statements, telemetry sample SQL, or secrets. Keep these mounts read-only, generated from approved target-environment evidence, and separate from raw `pg_stat_statements` exports, PostgreSQL logs, or support bundles.

If operators claim `VECTOR_ISOLATION_MODE=pgvector_partitioned_by_org`, mount reviewed live `romeo.pgvector-physical-isolation-review.v1` evidence into the app pod and set `env.PGVECTOR_PHYSICAL_ISOLATION_EVIDENCE_PATH`. Generate that evidence outside the app process with `pnpm review:pgvector-isolation -- --output ...` after the selected database is migrated from the greenfield baseline. `/api/v1/admin/readiness` fails claimed partitioned pgvector mode without passed live evidence, and `/api/v1/admin/rag/posture` returns only evidence status, partition/index counts, and redaction booleans.

If operators claim external-vector isolation through Qdrant, mount reviewed live `romeo.qdrant-live-evidence.v1` evidence into the app pod and set `env.QDRANT_LIVE_EVIDENCE_PATH`. Generate that evidence outside the app process with `pnpm smoke:qdrant:live -- --url ... --collection ... --confirm-mutation --output ...` against the selected collection. `/api/v1/admin/rag/posture` returns only evidence status, policy names, health/query/delete booleans, and redaction booleans; it does not return the mounted path, evidence body, endpoint, collection, API key, namespace values, partition values, payload values, point IDs, or vectors.

If operators want the running admin UI/API to display deployment-specific data-rights retention proof, generate reviewed metadata-only files with `pnpm evidence:data-rights-retention -- --control operational_logs --retention-days ... --output ...` and `pnpm evidence:data-rights-retention -- --control backups --retention-days ... --output ...`, mount them read-only into the app pod, then set `env.DATA_RIGHTS_OPERATIONAL_LOG_RETENTION_EVIDENCE_PATH` and `env.DATA_RIGHTS_BACKUP_RETENTION_EVIDENCE_PATH`. `GET /api/v1/governance/data-rights/coverage` reports only evidence status, retention days, destruction-validation/encryption booleans, reviewed-system counts, and failure codes; it does not return mounted paths, evidence bodies, raw log lines, backup locations, bucket names, object keys, ticket text, system hostnames, URLs, or secrets. Keep the generated files separate from raw logging-platform exports, backup manifests with object keys, and support bundles. Releases that claim these live retention/destruction controls should also run `pnpm ga:checklist -- --require-data-rights-retention-live`; `pnpm ga:target-preflight` then requires the reviewed-evidence confirmation env vars and bounded retention-day env vars before reporting the Phase 33 live gate ready.

Production installs should expose `/api/v1/admin/readiness` only to admins and check it before traffic cutover. Critical findings mean the release is not ready for shared or enterprise use. For identity hardening, readiness checks production-shaped local MFA encryption keys, local auth fallback posture, enabled OIDC provider cards with missing per-provider issuer/client config, disabled secret-resolution posture for configured provider secret refs, and invalid persisted provider secret-ref schemes without returning raw issuer paths, client IDs, or secret refs. When GA checklist, target-preflight, target-plan, target-execution, or bundle files are mounted through the documented `GA_*_PATH` variables, readiness also reports a metadata-only `ga_evidence` check; missing GA mounts remain informational, while blocked, failed, or invalid mounted GA evidence is a critical readiness finding without returning mounted paths, evidence bodies, raw failure strings, exception owner/rationale text, command text/output, tokens, or environment values.

Run Postgres schema validation after migrations and before app traffic cutover. The same command applies to CloudNativePG-managed clusters and external hosted Postgres because it only consumes `DATABASE_URL`:

```sh
pnpm review:baseline -- --strict --output dist/release/greenfield-baseline-review.json
DATABASE_URL="$DATABASE_URL" pnpm validate:postgres -- --output dist/release/postgres-schema-validation.json
```

The baseline review command is a release gate for the greenfield migration file; it checks pgvector ordering, required tables/indexes, cascade foreign keys, lifecycle columns, destructive statement absence, and PostgreSQL identifier lengths. The validation command checks the live database for the required pgvector extension, baseline tables, and baseline indexes, and writes sanitized evidence when `--output` is supplied.

Postgres backups should be scheduled outside the request path using the same database credentials as the app, or a narrower role with backup privileges:

```sh
DATABASE_URL="$DATABASE_URL" pnpm backup:postgres -- --output backups/romeo-postgres.dump --retention-days 30
```

The backup command writes a `*.manifest.json` evidence file with bytes, SHA-256, retention metadata, and a redacted database identifier. For Kubernetes schedules, start from `deploy/helm/postgres-backup-cronjob.example.yaml` and use an operations image that includes Node, pnpm, the Romeo scripts, and PostgreSQL client tools. Store `DATABASE_URL`, `POSTGRES_BACKUP_UPLOAD_URL`, `POSTGRES_BACKUP_MANIFEST_UPLOAD_URL`, `POSTGRES_BACKUP_RETENTION_DAYS`, and optional `POSTGRES_BACKUP_UPLOAD_TIMEOUT_MS` in the referenced Secret or Helm values. Presigned URLs are read from environment variables so they do not appear in command arguments, and each upload PUT is bounded by the configured timeout. `pnpm smoke:postgres:backup-upload-failure` records local failure-mode evidence with redacted upload URL metadata and explicit proof that raw presigned URLs, upload bodies, command output, database URLs, and environment values were not returned. Backup targets must be encrypted: use provider-managed encrypted buckets, KMS-backed buckets, or encrypted storage classes for dumps, manifests, object-store backups, WAL archives, and evidence stores. Restore evidence should include manifest SHA-256 verification, redacted source/target identifiers, encryption posture, retention days, and isolated-target confirmation without database URLs, presigned URLs, bucket credentials, backup object keys, or KMS key material.

Run restore only into an explicitly selected target database and require the destructive confirmation flag:

```sh
DATABASE_URL="$RESTORE_DATABASE_URL" POSTGRES_RESTORE_DOWNLOAD_URL="$PRESIGNED_BACKUP_GET_URL" pnpm restore:postgres -- --input backups/romeo-postgres.dump --expected-sha256 "$BACKUP_SHA256" --confirm
```

For DR evidence, run the same restore through an isolated drill database URL:

```sh
DRILL_DATABASE_URL="$ISOLATED_RESTORE_DATABASE_URL" POSTGRES_RESTORE_DOWNLOAD_URL="$PRESIGNED_BACKUP_GET_URL" pnpm drill:postgres-restore -- --input backups/romeo-postgres.dump --expected-sha256 "$BACKUP_SHA256" --confirm-isolated-target
```

Object-store backups use the same S3-compatible contract as the app and should be scheduled alongside database backups unless the backing store already has independently verified versioned backups. The backup manifest contains object keys, byte counts, SHA-256 hashes, content types, and redacted store metadata; it must be retained with the matching database backup because database rows reference object keys:

```sh
S3_ENDPOINT="$S3_ENDPOINT" S3_BUCKET="$S3_BUCKET" S3_ACCESS_KEY_ID="$S3_ACCESS_KEY_ID" S3_SECRET_ACCESS_KEY="$S3_SECRET_ACCESS_KEY" pnpm backup:object-store -- --output-dir backups/object-store --manifest-output backups/object-store/manifest.json
```

Restore objects into an explicitly selected target bucket before starting the restored app:

```sh
RESTORE_S3_ENDPOINT="$RESTORE_S3_ENDPOINT" RESTORE_S3_BUCKET="$RESTORE_S3_BUCKET" RESTORE_S3_ACCESS_KEY_ID="$RESTORE_S3_ACCESS_KEY_ID" RESTORE_S3_SECRET_ACCESS_KEY="$RESTORE_S3_SECRET_ACCESS_KEY" pnpm restore:object-store -- --manifest backups/object-store/manifest.json --confirm
```

For DR evidence, restore into an isolated target bucket and verify every manifest object by SHA-256:

```sh
RESTORE_S3_ENDPOINT="$ISOLATED_RESTORE_S3_ENDPOINT" RESTORE_S3_BUCKET="$ISOLATED_RESTORE_S3_BUCKET" RESTORE_S3_ACCESS_KEY_ID="$ISOLATED_RESTORE_S3_ACCESS_KEY_ID" RESTORE_S3_SECRET_ACCESS_KEY="$ISOLATED_RESTORE_S3_SECRET_ACCESS_KEY" pnpm drill:object-store-restore -- --manifest backups/object-store/manifest.json --confirm-isolated-target
```

CloudNativePG and external hosted Postgres modes both need the same combined DR acceptance test: restore Postgres, restore object storage, run schema validation, start Romeo with seeded login disabled, pass readiness, and read back representative chats, knowledge records, query results, and stored artifacts through the API.
