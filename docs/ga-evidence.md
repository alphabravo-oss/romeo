# GA Evidence Checklist

Romeo GA acceptance is tracked by `pnpm ga:checklist`. The command reads expected evidence files under `dist/ci` and `dist/release`, validates key schema/status fields plus gate-specific live-readback and local security-evidence contracts, and writes a redacted `romeo.ga-checklist.v1` document.

Generate a draft checklist:

```sh
pnpm ga:checklist -- --output dist/release/ga-checklist.json
```

Run strict promotion validation:

```sh
pnpm ga:checklist -- --strict --output dist/release/ga-checklist.json
```

Strict mode exits nonzero when any GA-required gate is missing, failed, or not covered by a valid approved exception. It is expected to fail until the target tier has target-quality, live Kubernetes, Kubernetes worker CronJob/crash recovery, NetworkPolicy/CNI enforcement, tiered-RAG isolation, release readback, hosted CI/branch-protection governance where claimed, alert-firing, DR, and load/soak evidence.

For a full-product enterprise completion claim, use the strict full-product profile instead of manually assembling every optional `--require-*` flag:

```sh
pnpm ga:checklist -- --strict --profile full-product-enterprise --output dist/release/ga-checklist.json
```

`--profile full-product-enterprise` can also be selected with `GA_CHECKLIST_PROFILE=full-product-enterprise` or `GA_REQUIRE_FULL_PRODUCT_ENTERPRISE=true`. It keeps the default GA gates and additionally requires Qdrant live isolation, Qdrant DR, hosted CI/branch-protection governance, KEDA scaler proof, browser automation runner proof, target identity proof, live data connector worker/CNI proof, live tool-dispatch worker/CNI proof, production voice provider proof, production notification adapter proof, target analytics authorization/export proof, target-quality vector route comparison, data-rights retention proof, billing operations proof, audit-integrity proof, tenant purge proof, support-bundle proof, target resilience drills, and target Postgres operational evidence. Use this profile for Romeo full-product completion; the individual flags remain available for narrower release claims.

Live target evidence must include a valid `generatedAt` timestamp from the gate-specific collector and must be fresh at checklist time. The GA validator rejects timestamp-less, future-dated beyond normal clock skew, or stale live evidence for target-quality, Kubernetes live/worker/NetworkPolicy/DR/tiered-RAG/load-soak, live edge enforcement, live alert firing, and optional Qdrant live/DR gates. Re-run the collector in the selected target environment instead of reusing old artifacts.

Before live target collection, run the target preflight against a draft checklist:

```sh
pnpm ga:target-preflight -- --checklist dist/release/ga-checklist.json --output dist/ci/ga-target-preflight.json
```

The preflight writes `romeo.ga-target-preflight.v1` evidence that maps blocked GA gates to their live collection commands and checks command availability, Kubernetes reachability, required credential environment presence, release artifact files, release-readback plan shape, CI governance review/repository/run-selector posture, target-quality replay inputs, live edge admin/WAF/body/rate-limit inputs, identity review posture, analytics authorization review posture, billing-operations review posture, tenant-purge review posture, support-bundle review posture, Postgres operational target/telemetry/archival prerequisites, alert rule/category coverage, target API origin, Prometheus origin, optional Qdrant live-isolation prerequisites, and optional Qdrant DR prerequisites. It is operator-readiness evidence only and does not satisfy GA gates; live evidence files still need to be generated by the gate-specific commands. The preflight output omits command output, raw environment values, tokens, evidence bodies, unsafe absolute evidence paths, target-quality replay contents, repository slugs, GitHub run IDs, branch names, CI job logs, raw GitHub API responses, Kubernetes Secret names/keys/values, identity provider endpoints, IdP responses, directory entries, LDAP DNs, SAML assertions, group names, user emails, analytics CSV rows, eval inputs/outputs, usage metadata, job payloads, Postgres database URLs/hosts, SQL, query text, lock statements, edge probe payloads, edge query/header values, billing payloads, customer identifiers, tenant-purge object keys, vector values, backup locations, operational log bodies, support bundle bodies, alert payloads, and Qdrant collection/API-key values.

Compile an ordered target evidence plan from reviewed preflight output:

```sh
pnpm ga:target-plan -- --preflight dist/ci/ga-target-preflight.json --output dist/ci/ga-target-evidence-plan.json
```

The plan writes `romeo.ga-target-evidence-plan.v1` with phase order, gate order, safe command text, required command names, required/optional/any-of environment variable names, required file paths, evidence target paths, blocked reason codes, per-gate `operatorAction` state, and per-phase summaries. It does not run commands and does not satisfy GA gates. The plan output omits command output, raw environment values, tokens, raw preflight check bodies, unsafe absolute paths, and evidence bodies.

Generate a redacted target environment skeleton from the reviewed plan:

```sh
pnpm ga:target-env-template -- --plan dist/ci/ga-target-evidence-plan.json --output dist/ci/ga-target-env-template.json --env-output dist/ci/ga-target.env.example
```

The JSON report writes `romeo.ga-target-env-template.v1` with required command names, required environment-variable names, any-of variable groups, optional variable names, required file placeholders, evidence target paths, and stable blocker codes grouped by gate. The optional `.env` skeleton contains blank assignments only; it never includes command text, command output, environment values, tokens, evidence bodies, or unsafe absolute paths. Populate a private copy in the target evidence-collection environment, then pass it directly to the tooling instead of shell-sourcing it:

```sh
pnpm ga:target-preflight -- --checklist dist/release/ga-checklist.json --output dist/ci/ga-target-preflight.json --env-file dist/ci/ga-target.env.private
```

The env-file parser accepts simple dotenv-style assignments, skips blank placeholders, does not evaluate shell syntax or variable interpolation, and records only counts, variable names, warning codes, and redaction flags. Rerun preflight until intended gates are ready, then execute only ready gates.

After reviewing the plan, operators can batch-run only gates whose `operatorAction.state` is `ready_to_run`:

```sh
GA_TARGET_EXECUTE_CONFIRM=run-ready-gates pnpm ga:target-execute-ready -- --plan dist/ci/ga-target-evidence-plan.json --output dist/ci/ga-target-execution.json --env-file dist/ci/ga-target.env.private --continue-on-failure
```

The execution report writes `romeo.ga-target-execution.v1` with selected gate counts, command hashes, exit status, timing, skipped blocked/redacted gates, env-file metadata counts, and explicit redaction flags. It does not store command text, command output, env-file values, or env-file bodies, and it does not replace the gate-specific evidence files generated by those commands. Without `GA_TARGET_EXECUTE_CONFIRM=run-ready-gates` or `--confirm-run-ready-gates`, the command writes a non-mutating dry-run report and exits with confirmation required.

For releases that claim hosted CI and branch-protection governance are complete, make that proof strict:

```sh
pnpm ga:checklist -- --strict --require-ci-governance-live --output dist/release/ga-checklist.json
```

`--require-ci-governance-live` can also be set with `GA_REQUIRE_CI_GOVERNANCE_LIVE=true`. It adds the `phase22.ci_governance_live` gate for `dist/ci/branch-protection-plan.json`, `dist/ci/hosted-ci-run-verification.json`, and `dist/ci/branch-protection-verification.json`. Target preflight requires `CI_GOVERNANCE_EVIDENCE_REVIEWED=true`, `GITHUB_REPOSITORY`, one of `GITHUB_TOKEN` or `GH_TOKEN`, and one of `GITHUB_CI_RUN_ID` or `GITHUB_CI_HEAD_SHA`. The validator rejects dry-run hosted CI evidence, incomplete required status-check planning, branch policies with fewer than two approvals, missing branch-protection verification checks, blockers, repository-slug leakage, raw API/log/run URL leakage, and token or secret leakage.

After collecting and reviewing `romeo.live-edge-enforcement.v1`, operators can mount it read-only and set `EDGE_ENFORCEMENT_EVIDENCE_PATH` so `GET /api/v1/admin/edge-security/posture` exposes sanitized live edge evidence posture for admins and frontend clients. The endpoint reports status, required-check coverage, WAF/body-limit/rate-limit summaries, header counts, warning codes, and redaction booleans only; it does not return mounted paths, evidence bodies, target origins, API keys, header values, probe payloads, query values, request bodies, response bodies, or secret values.

Local regression coverage for the preflight starts with:

```sh
pnpm smoke:ga:target-preflight-contract -- --output dist/ci/ga-target-preflight-contract-smoke.json
pnpm smoke:ga:target-plan-contract -- --output dist/ci/ga-target-evidence-plan-contract.json
pnpm smoke:ga:target-env-template-contract -- --output dist/ci/ga-target-env-template-contract-smoke.json --env-output dist/ci/ga-target.env.example
pnpm smoke:ga:target-execution-contract -- --output dist/ci/ga-target-execution-contract-smoke.json
```

The target-preflight contract smoke proves private env-file loading can satisfy preflight environment checks while the evidence omits raw values and file bodies. The execution contract smoke writes a passed `romeo.ga-target-execution-contract-smoke.v1` wrapper while embedding a synthetic failed-gate fixture, proving private env-file values reach child commands, failed-gate accounting works, and command text/output still do not leak into execution evidence.

If the selected deployment claims live Qdrant external-vector isolation, require live scoped-isolation evidence:

```sh
pnpm ga:checklist -- --strict --require-qdrant-live --output dist/release/ga-checklist.json
```

`--require-qdrant-live` can also be set with `GA_REQUIRE_QDRANT_LIVE=true`. It adds the `phase32.qdrant_live_evidence` gate for `dist/ci/qdrant-live-evidence.json`. Generate the evidence with `QDRANT_LIVE_EVIDENCE_REVIEWED=true pnpm smoke:qdrant:live -- --url "$QDRANT_URL" --collection "$QDRANT_COLLECTION" --api-key "$QDRANT_API_KEY" --namespace-policy "$VECTOR_NAMESPACE_POLICY" --partitioning-policy "$VECTOR_PARTITIONING_POLICY" --confirm-mutation --output dist/ci/qdrant-live-evidence.json` after reviewing that the selected collection, credential scope, namespace policy, and partitioning policy match the runtime deployment that will mount `QDRANT_LIVE_EVIDENCE_PATH`. The validator rejects dry-run evidence, `VECTOR_NAMESPACE_POLICY=none`, incomplete scoped query/delete proof, missing trap exclusion, missing filter proof, and redaction leaks. Target preflight requires `QDRANT_LIVE_EVIDENCE_REVIEWED=true`, `QDRANT_URL`, `QDRANT_COLLECTION`, `QDRANT_API_KEY`, `VECTOR_NAMESPACE_POLICY`, and `VECTOR_PARTITIONING_POLICY`, and reports only safe URL origin, configured booleans, policy names, and redaction flags.

```sh
pnpm ga:checklist -- --strict --require-qdrant-dr --output dist/release/ga-checklist.json
```

`--require-qdrant-dr` can also be set with `GA_REQUIRE_QDRANT_DR=true`. ```sh

```

`--require-keda` can also be set with `GA_REQUIRE_KEDA=true`. Admins can expose the generated checklist to the API by mounting the file into the app container and setting `GA_CHECKLIST_PATH` to that path. They can also mount generated target-preflight evidence with `GA_TARGET_PREFLIGHT_PATH` when the running admin API should show live-gate prerequisite readiness, mount generated target-plan evidence with `GA_TARGET_PLAN_PATH` when operators want ordered next-action planning, mount generated target-execution evidence with `GA_TARGET_EXECUTION_PATH` when operators want batch-run status, and mount the GA evidence bundle manifest with `GA_EVIDENCE_BUNDLE_PATH` when admins should see release-candidate/final-promotion bundle posture. `GET /api/v1/admin/ga/evidence-posture` and `client.admin.gaEvidencePosture()` return a metadata-only posture report with summary counts, sanitized gate status, checklist target profile (`default-ga` or `full-product-enterprise`), the `fullProductEnterpriseRequired` switch, optional target gate booleans, required live blockers, joined `liveGateReadiness`, sanitized preflight gate readiness, sanitized target-plan phase/gate order, safe command text, command/env/file/check status, sanitized target-execution command hashes/status/timings/skip reasons/env-file metadata counts, bundle release/version, requirements, GA summary, evidence/check counts, blocker codes, and explicit redaction flags. Checklist evidence and exception `failures` arrays are collapsed to Romeo-owned presence codes instead of returning raw failure strings from mounted files. The joined readiness projection maps each required live blocker to its matching preflight status, safe command, evidence/check counts, blocked reason codes, and stable warning codes so operator UIs can show the next required action without correlating raw evidence files. The endpoint does not return configured absolute paths, bundle evidence paths, bundle blocker messages, evidence file bodies, raw command text, raw command output, raw environment values, env-file values, env-file bodies, tokens, exception owner/approver/rationale/risk text, raw checklist failure strings, raw target-plan check bodies, or unsafe raw evidence paths. When `GA_CHECKLIST_PATH`, `GA_TARGET_PREFLIGHT_PATH`, `GA_TARGET_PLAN_PATH`, `GA_TARGET_EXECUTION_PATH`, or `GA_EVIDENCE_BUNDLE_PATH` is unset, that section reports `not_configured` rather than reading from `dist` implicitly.

Admins can expose reviewed release readback evidence to the API by mounting the plan, raw readback metadata, and validation files and setting `RELEASE_READBACK_PLAN_PATH`, `RELEASE_READBACK_EVIDENCE_PATH`, and `RELEASE_READBACK_VALIDATION_PATH`. `GET /api/v1/admin/release-readback/posture` and `client.admin.releaseReadbackPosture()` return a metadata-only posture report with plan/readback/validation status, required package/image/chart/asset counts, credentialed registry-readback booleans, verification counts, warning codes, and redaction-proof counts. The endpoint does not return mounted paths, registry URLs, OCI image refs, Helm repository URLs, release-asset URLs, package tarballs, raw registry responses, raw readback bodies, OCI manifests, Helm repository bodies, token values, or secret values. When those env vars are unset, the sections report `not_configured` rather than reading from `dist` implicitly.

  --source-namespace romeo-cnpg-source \
  --restore-namespace romeo-cnpg-restore \
  --source-database-url-secret romeo-pg-app:uri \
  --restore-database-url-secret romeo-pg-restore-app:uri \
  --skip-build \
  --image registry.example/romeo/app:1.2.3@sha256:<digest> \
  --output dist/ci/kubernetes-cloudnativepg-dr.json
```

Both files must be live `romeo.kubernetes-dr-smoke.v1` evidence with `status=passed`, `mode=live`, the expected `databaseMode`, isolated source/restore namespaces, backup/restore/schema/readback checks, and redacted log evidence. The GA checklist requires source and restore pod-log scan count metadata plus generated-secret and raw-content sentinel redaction proof. Dry-run DR output is planning evidence only. Use isolated restore namespaces and restore databases because the Postgres and object-store restore jobs are destructive after their confirmation guards.

The optional gate requires live `romeo.kubernetes-keda-smoke.v1` evidence with KEDA CRD/readiness checks, ScaledJob/TriggerAuthentication readback, worker API-key and Postgres Secret refs, due webhook backlog creation, worker Job completion, retry readback, nonzero target namespace and KEDA operator log scan counts, and redaction proof for admin API key, worker API key, database URL, webhook signing secret, webhook payload sentinel, webhook URL sentinel, and any extra secret sentinels.

Generate backup-upload failure evidence with:

pnpm smoke:postgres:backup-upload-failure -- --output dist/ci/postgres-backup-upload-failure-smoke.json

Generate live alert-firing evidence after forcing provider, queue-lag, dead-letter, and backup-failure drills in the selected monitoring stack:

```sh
PROMETHEUS_URL="https://prometheus.example.com" \
PROMETHEUS_BEARER_TOKEN="$PROMETHEUS_BEARER_TOKEN" \
ALERTMANAGER_URL="https://alertmanager.example.com" \
ALERTMANAGER_BEARER_TOKEN="$ALERTMANAGER_BEARER_TOKEN" \
pnpm smoke:alerts:live -- --output dist/ci/live-alert-firing.json
```

The default alert set requires `RomeoProviderCircuitOpen`, `RomeoBackgroundJobQueuedLag`, `RomeoBackgroundJobDeadLetters`, and `RomeoPostgresBackupJobFailed`. The live evidence must include explicit redaction flags proving bearer tokens, raw Prometheus responses, raw Alertmanager responses, raw URLs, and raw alert payloads were not returned. Dry-run alert evidence is planning evidence only and is rejected by `pnpm ga:checklist`.

Admins can expose reviewed live alert-firing evidence to the API by mounting the file read-only and setting `ALERT_FIRING_EVIDENCE_PATH`. `GET /api/v1/admin/alert-firing/posture` and `client.admin.alertFiringPosture()` verify that every configured required alert name appears in the Prometheus firing readback before reporting the posture as ready, then return only evidence status, live/dry-run mode, required-check coverage, provider/queue/backup category counts, Prometheus/Alertmanager readback counts, warning codes, and redaction booleans. They do not return the mounted path, evidence body, Prometheus or Alertmanager URLs, bearer tokens, alert names, labels, annotations, raw responses, raw alert payloads, or secret values.

Optional exceptions use this shape:

```json
{
  "schemaVersion": "romeo.ga-exceptions.v1",
  "exceptions": [
    {
      "gateId": "phase35.docs_command_check",
      "owner": "owner@example.com",
      "approvedBy": "approver@example.com",
      "seniorApproval": true,
      "expiresAt": "2026-12-31T23:59:59.000Z",
      "rationale": "Narrow deployment scope excludes this surface.",
      "riskAcceptance": "Accepted for this release with follow-up ticket HAM-123."
    }
  ]
}
```

Security-critical gates require `seniorApproval: true`. Some gates, such as baseline migration review, Postgres schema validation, repository conformance, Compose DR, Kubernetes live validation, and credentialed release readback, are not exception-eligible for GA.

Treat the exception input file as sensitive release-approval material. The generated `romeo.ga-checklist.v1` stores only exception gate ID, validation status, expiry, senior-approval posture, and failure codes; it does not copy owner, approver, rationale, or risk-acceptance text into release evidence.
