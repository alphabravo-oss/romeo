# RAG

RAG is implemented around Romeo-owned knowledge bases, Postgres source-of-truth rows, pgvector-backed embeddings, optional Qdrant runtime routing with request-level namespace/partition filters, a native tiered-query API for authorized user-private, workspace, org-published, and approved shared knowledge bases, an org-scoped RAG policy API, and a sanitized admin posture API. The backend also has mounted live-evidence contracts for partitioned pgvector claims, Qdrant health/namespace/delete evidence, Qdrant restored-stack consistency, and Kubernetes tiered-RAG smoke. Enterprise-product completion still requires executing those target-deployment harnesses in the selected cluster/vector environment before GA claims.

Default direction:

- Postgres remains source of truth.
- pgvector is the default local vector store.
- Qdrant is the first external scale-out vector store.
- document chunks store text and metadata in Postgres.
- provider-generated embeddings are stored separately in `knowledge_chunk_embeddings` with pgvector `vector(1536)` data and an HNSW cosine index.
- external vector stores reference Postgres chunk ids.

The greenfield baseline migration should enable the `vector` extension before creating `knowledge_chunk_embeddings`. The table is keyed to chunk/source/knowledge-base ownership metadata and deduplicates one embedding per chunk/provider/model pair so reindexing can replace vectors without duplicating chunk text.

Provider embedding adapters now exist in `@romeo/providers` for OpenAI-compatible and Ollama endpoints. Controlled indexing jobs persist vectors into `knowledge_chunk_embeddings`, and the knowledge query service can re-embed the query with the selected provider/model before asking the repository for nearest stored chunk embeddings. Callers without `models:use` plus provider `use` permission fall back to the local lexical retriever so knowledge-only access does not trigger provider cost.

Agent runtime retrieval uses the same persisted-vector boundary for enabled knowledge-base bindings when the run subject has provider access, then falls back to the local lexical retriever. `@romeo/db` includes a focused pgvector helper for `knowledge_chunk_embeddings` nearest-neighbor search using native cosine-distance `ORDER BY`, explicit `org_id`, `workspace_id`, `knowledge_base_id`, provider, model, and dimension predicates before similarity ranking, finite-vector validation, dimension checks, bounded result limits, and chunk-ID tie breaking. It also exposes `PgKnowledgeEmbeddingRepository`, `createKnowledgeEmbeddingRepositoryFragment(...)`, and `composeRepositoryFragments(...)` so the embedding methods can be mounted into the eventual database-backed repository without a broad placeholder class. Hybrid query results now use a focused rank-fusion helper instead of blending raw vector and lexical scores directly; chunks that appear in both channels are boosted, while single-channel hits remain stable and bounded by channel rank. Remaining RAG work is to tune customer-specific retrieval weights only after real corpora expose a need.

Native tiered retrieval is available through `POST /api/v1/knowledge-bases/query` and `client.knowledge.queryTiered(...)`. The request supplies bounded `knowledgeBaseIds`, query text, and optional `maxResultsPerTier` budgets. The service compiles an authorization-filtered plan before retrieval, sorts authorized entries by tier priority, applies the org RAG policy's enabled tiers/default budgets/max budget caps, classifies caller-owned bases as `user_private`, other authorized same-workspace bases as `workspace`, policy-assigned bases as `org` or `shared`, then runs the existing per-KB vector/lexical retrieval path for each authorized entry. Assigned `org` and `shared` tiers can cross workspace boundaries, but still require an explicit `use` grant. Non-admin cross-org shared retrieval additionally requires the subject org policy to assign the external KB to `shared` and the resource-owning org to hold an explicit subject/group `use` grant; unassigned cross-org KBs are skipped even if a grant exists. Responses include `plan.entries`, `plan.policy`, redacted vector posture (`vectorDriver=pgvector`, `isolationMode=shared_row_scope`, external vector driver/config/routing booleans, and namespace policy), skipped reason counts without denied IDs, and hits annotated with `knowledgeBaseId`, `workspaceId`, `orgId`, `tier`, metadata-only `permissionReason`, and `retrievalRoute`. `retrievalRoute` reports only stable route metadata: pgvector/external-vector/lexical/legacy mode, vector-store driver, external-vector attempted/used booleans, optional provider ID/model/dimensions, and optional fallback reason. If no submitted base is authorized or all authorized bases are disabled by policy, the API fails closed with `knowledge_retrieval_plan_empty` and does not echo denied IDs or query text.

Admin RAG/vector posture is available through `GET /api/v1/admin/rag/posture` and `client.admin.ragPosture(...)`. The report is aggregate-only for the caller's org: active vector driver and isolation flags, sanitized external-store deployment posture (`disabled` or `qdrant`, endpoint/collection/credential configured booleans, credential-ref validity and scheme, namespace/partition policy, configured/routing-active booleans), corpus/source/chunk/embedding coverage counts, stale source and embedding counts, failed/queued/running knowledge job counts, lexical fallback reason codes, mounted `PGVECTOR_PHYSICAL_ISOLATION_EVIDENCE_PATH` and `QDRANT_LIVE_EVIDENCE_PATH` status summaries, and warning severities. It deliberately omits database URLs, vector endpoints, namespace and collection names, secret refs, evidence paths, evidence bodies, knowledge-base names, source names, object keys, chunk text, embedding vectors, job IDs, job payloads, and query text. If `EXTERNAL_VECTOR_STORE_DRIVER=qdrant` is configured but `routingActive=false`, deployment wiring is visible but runtime routing is not active for that service instance. When `routingActive=true`, Romeo still persists provider embeddings in Postgres, mirrors scoped vectors to Qdrant with deterministic `VECTOR_NAMESPACE_POLICY` and optional `VECTOR_PARTITIONING_POLICY` tokens, queries Qdrant with namespace/partition plus org/workspace/knowledge/source/provider/model/dimension filters, deletes external source vectors through the same scope filters, and falls back to pgvector if Qdrant query fails. Admin readiness also performs a bounded metadata-only Qdrant collection health check before passing the vector-store readiness check; it reports collection health status/failure class without endpoint, collection, namespace, or secret values. If `VECTOR_ISOLATION_MODE=pgvector_partitioned_by_org`, readiness fails until passed live `romeo.pgvector-physical-isolation-review.v1` evidence is mounted. If `VECTOR_ISOLATION_MODE` claims `external_namespace_per_org`, `external_collection_per_org`, or `dedicated_vector_store_per_org`, readiness fails until Qdrant routing is active and `QDRANT_LIVE_EVIDENCE_PATH` points to satisfied live evidence whose namespace and partitioning policies match the deployment config; `external_namespace_per_org` additionally requires `VECTOR_NAMESPACE_POLICY=org`.

Org RAG policy is available through `GET/PATCH /api/v1/admin/rag/policy` and `client.admin.ragPolicy()` / `client.admin.updateRagPolicy(...)`. The policy is stored in `system_settings`, so it adds no migration file. Implemented enforcement covers enabled tiers plus default and maximum result budgets for user-private/workspace/org/shared retrieval, policy-owned `knowledgeBaseTierAssignments` for `org` and `shared` KBs, and the allowed embedding provider/model list before provider-backed indexing, before Qdrant upsert, and during query-time persisted-vector selection before external vector search. Current source deletion explicitly clears source embeddings and chunks, deletes stored source objects, sends scoped Qdrant delete requests when external routing is active, and writes metadata-only retention evidence with counts and policy posture while excluding object keys, file names, chunk text, embedding vectors, and raw source content. Source reindex tombstones scoped Qdrant source vectors only after the replacement source/chunk transaction succeeds, so stale external points do not survive chunk ID rotation and a failed reindex does not delete the previous external index. Data-residency tags plus explicit external-vector namespace/partitioning policy, Postgres-authoritative DR/reindex strategy, metadata-only export policy, and restore-validation posture are stored as stable metadata only; policy update audits store changed categories and counts only, not provider IDs, model names, assigned KB IDs, tags, query text, or corpus content. Governed data exports include RAG/vector policy posture only as sanitized metadata and continue to exclude vector values, vector IDs, endpoints, collection names, namespace values, and secret refs.

## Enterprise Isolation Target

Romeo should support graduated vector isolation without making Docker Compose unnecessarily complex:

- Local Compose and single-org installs: one Postgres database with pgvector, strict `org_id`, `workspace_id`, `knowledge_base_id`, `source_id`, and resource-grant predicates on every retrieval path.
- Team and enterprise installs: partition high-volume chunk and embedding tables by org or tenant tier where query plans justify it, while preserving the same `DATABASE_URL` and migration contract.
- Regulated orgs: optionally assign a dedicated Postgres schema or database to an org through deployment-managed configuration and readiness checks.
- Scale-out retrieval: optionally route selected orgs to an external vector-store namespace or collection, with Qdrant as the first supported target and Postgres chunk ids remaining authoritative.
- High-side or DoD-style deployments: support dedicated clusters, accounts/projects, object buckets, KMS keys, and vector namespaces per environment or org instead of shared multi-tenant infrastructure.

Vector-store selection and connection details should be deployment configuration, not user-editable application secrets. Admin APIs may expose sanitized posture such as active driver, external driver, isolation mode, namespace policy, configured booleans, credential-ref scheme, mounted evidence status, index status, and readiness warnings, but must not return database URLs, vector-store endpoints, collection names, secret refs, evidence paths, evidence bodies, embedding text, raw chunks, provider keys, or query content. The implemented posture API reports the Compose/Kubernetes default pgvector shared-row-scope mode, deployment-managed Qdrant wiring and routing-active state, partitioned pgvector evidence posture, and Qdrant live-evidence posture through sanitized booleans and counts. High-isolation external-vector modes now fail readiness unless active routing and reviewed live evidence agree on the configured namespace and partition policies, preventing declaration-only isolation claims.

## Tiered Retrieval Model

Tiered RAG should compile an authorization-filtered retrieval plan before any lexical or vector query runs. A user query can draw from multiple tiers only when the subject has explicit `use` or `read` permission:

- user-private knowledge bases
- team or workspace knowledge bases
- org-published knowledge bases
- admin-approved shared corpora
- optional cross-org/shared-library corpora where policy allows it

The retrieval plan must include stable scope metadata for each tier: org, workspace, knowledge base, source filters, permission reason, isolation driver, max-result budget, and sanitized route metadata. Vector searches must include the same scope filters in the database or external vector-store query, then post-filter the returned chunk ids against Postgres authorization as defense in depth. Query results should preserve citation provenance, tier, source, permission reason, and route mode without exposing hidden source metadata.
