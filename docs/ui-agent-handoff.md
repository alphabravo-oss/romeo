# Romeo UI Agent Handoff

Status date: 2026-07-06.

## Goal

Rework `apps/app` into a chat-first Romeo UI that uses OpenWebUI only as visual and interaction reference while staying on Romeo's own API and domain model. Romeo is its own product; do not import OpenWebUI code, copy its product-specific flows, or treat OpenWebUI route parity as required unless a future backlog item explicitly says so.

## API Readiness

The UI can start now against real contracts. Romeo has a stable native `/api/v1` surface, OpenAPI at `/api/v1/openapi.json`, endpoint docs at `/api/v1/docs`, a generated TypeScript client in `packages/api-client`, and current web wrappers in `apps/app/src/api`. The default OpenAPI document includes named schemas for the bootstrap current-user profile, core chat/run records, messages, attachments, message feedback state, comments, OpenAI-compatible model/chat/embedding payloads, approval summaries, approval decisions, run events, and `run.continuing` payloads; OpenWebUI-shaped bridge schemas are omitted unless `OPENWEBUI_COMPATIBILITY_ENABLED=true` is used for deliberate bridge validation. Native Romeo endpoints and SDK methods are authoritative for new UI work.

Ready for core UI work:

- Deploy-time tenancy context is server-authoritative on `GET /api/v1/me` as `deployment.tenancyMode`, with values `single` or `multi`. Use that field to hide org/global scope switching in single-tenant installs and show it only in multi-tenant installs; do not require a separate frontend build-time env var for the normal Romeo UI.

## Backend Caveats

These should not block the chat-first UI pass:

- Out-of-process tool-dispatch worker support exists, including bearer/API-key/OAuth client-credentials auth through worker-local payloads and env/Vault/AWS/GCP/Azure secret resolvers. Backend/API managed encrypted object-store payload handoff now exists behind `TOOL_DISPATCH_PAYLOAD_STORE_DRIVER=object-store`, and the deployable worker can consume managed payloads through the active-lease payload API without a payload file. MCP Streamable HTTP dispatches use metadata-only claim transport hints so the worker can create `tools/call` JSON-RPC requests; UI surfaces should show connector/operation posture and request key names, not raw MCP arguments. That payload API is worker-only; UI surfaces should continue showing dispatch status and request key names, never raw payload values. Admin posture is available through `client.admin.toolDispatchPosture()` / `GET /api/v1/admin/tool-dispatch/posture`, with live evidence supplied by `TOOL_DISPATCH_LIVE_EVIDENCE_PATH`; it returns only execution-driver, payload-store, queue, worker/network-policy, warning, evidence-summary, MCP proof booleans/counts, and redaction posture. It never returns MCP arguments, MCP tool output, raw payload values, object-store keys, operation hosts, secret refs, or evidence bodies.
- Delegated connector OAuth now has provider-list/start, public callback completion with server-side replay rejection, redacted connection list, provider-backed revoke APIs, repository-backed refresh serialization, and GitHub connector use through `delegatedOAuthConnectionId`. The UI can show provider configuration posture, launch "Connect GitHub", list redacted linked-account rows from `/api/v1/delegated-oauth/connections`, let GitHub connector creation choose one linked connection instead of `secretRef`, and call `/api/v1/delegated-oauth/connections/{connectionId}/revoke`; final connection-management polish is still product backlog until the UI handles status, scopes, last-used, revoke status, and reauthorize affordances cleanly.
- Live model-driven tool-call orchestration now has backend API slices for run-scoped tool execution, replay protection, provider tool-call normalization, credentialed OpenAI-compatible streaming, provider tool-schema injection for built-ins and agent-bound worker-ready imported OpenAPI operations, sanitized `tool.requested` events, bounded inline continuation for single or batched non-approval built-in model-requested tools, metadata-only imported-operation dispatch enqueue, durable OpenAI-compatible approval wait/resume, unified metadata-only pending approval summaries, metadata-only approval/cancel/reject decisions for built-in and imported-operation approvals, worker-dispatch wait/resume, linked dispatch cancellation, and optional managed encrypted object-store payload references for queued dispatch jobs. When a run emits `run.waiting_tool_approval`, render the metadata-only approval state, keep the server `approvalRequestId`, optionally record the user decision with `client.tool.approveApproval(approvalRequestId)`, then submit the approved tool call through `client.tool.executeForRun(...)` / `POST /api/v1/runs/{runId}/tools/{toolId}/execute` with `approved: true`, `approvalRequestId`, and the user-approved input. Cancel or reject with `client.tool.cancelApproval(approvalRequestId)` / `client.tool.rejectApproval(approvalRequestId)`. Cancel/reject append sanitized `tool.failed` plus terminal `run.cancelled` events for waiting built-in run approvals, remove the approval from the queue, and prevent later replay approval. Imported operations now emit `run.waiting_tool_dispatch` with `jobId`, `toolName`, connector/operation IDs, request key names, `workerQueue`, and `payloadStorage`; `payloadStorage` may be `external_worker_secret_store_required` or `managed_encrypted_object_store`. Approved tool calls and worker readback resumes emit metadata-only `run.continuing` events before generation continues. Keep showing a waiting state until `run.continuing`, `message.started`, or terminal readback resumes the assistant response. Do not expect raw operation response bodies, rendered URLs, payload object keys, or raw payload values in run events or tool results. If the user cancels while waiting, reconnect or poll events and expect a terminal `run.cancelled`; do not attempt later approved tool execution for completed, failed, or cancelled runs.
- Browser automation worker APIs exist for backend/operator flows: claim, renew, screenshot/trace upload registration, complete, fail, and expire. Treat them like a worker/admin surface, not normal chat UI. Public readback remains metadata-only except server-issued screenshot/trace artifact URLs; retrieve artifact bytes through `/api/v1/browser-automation-artifacts/{artifactId}` so Romeo can enforce org/workspace access and private cache headers.
- Kubernetes live smoke, NetworkPolicy evidence, CloudNativePG live evidence, and GA release evidence remain product-completion gates.
- Exact OpenWebUI route parity is not a Romeo product requirement by default. Same-path OpenWebUI raw detail routes such as `/api/v1/chats/{id}` conflict with Romeo's native envelope route, and broader OpenWebUI routers should be implemented only after explicit product decisions.
- Persisted global/per-org auth-provider settings now exist for the provider app-store page through the settings APIs above and use managed secret refs without returning raw secret values. OIDC-family login is active through `/api/v1/auth/oidc/start?providerId=okta&orgId=...` and `/api/v1/auth/oidc/callback`; direct GitHub login is active through `/api/v1/auth/oauth2/start?providerId=github` and `/api/v1/auth/oauth2/callback`; LDAP and Active Directory login are active through `/api/v1/auth/ldap/login`; SAML login and metadata are active through `/api/v1/auth/saml/start`, `/api/v1/auth/saml/callback`, and `/api/v1/auth/saml/metadata`.

Never display raw tool payloads, connector secrets, tokens, provider errors, raw webhook bodies, or raw worker results. The backend deliberately returns metadata-only summaries for these paths.

Target feel:

- First screen is the usable chat workspace, not a dashboard or landing page.
- Left sidebar: compact brand, new chat button, chat history, optional agent/workspace affordances, admin/settings at the bottom.
- Center chat: narrow readable conversation column around 850px with lots of whitespace and no dashboard cards.
- Top chrome: minimal agent/model selector and lightweight actions, not a large toolbar.
- Composer: pinned bottom, centered, rounded input, icon buttons for attach, voice, stop, send.
- Empty state: assistant name, "How can I help you today?", compact suggestions.
- Messages: user messages right-aligned in rounded bubbles, assistant responses left-aligned with small avatar/name and tool/speech controls.
- Theme: neutral OpenWebUI-like gray scale, complete light/dark support, no decorative gradients or marketing treatment.

## Implementation Guardrails

- Keep files small. Split shell, sidebar, chat panel, message list, composer, settings entry points, and hooks instead of growing one large component.
- Reuse existing app structure: TanStack Router, TanStack Query, `lucide-react`, and `apps/app/src/styles/app.css` tokens.
- Use icon buttons where the action is standard; add accessible labels and titles.
- Do not create nested cards or a dashboard-first homepage.
- Do not put secrets, tokens, raw payloads, raw prompts beyond chat content, or raw provider errors into client logs or persistent client state.
- Preserve streaming behavior, cancel behavior, attachment limits, voice controls, and existing admin route access.
- Mobile must collapse or hide the sidebar cleanly and keep the composer reachable.

## Validation For The UI Pass

Minimum checks before handing back:

- `pnpm --filter @romeo/app check`
- `pnpm --filter @romeo/app test`
- `pnpm --filter @romeo/app build`
- Browser check at desktop and mobile widths against `http://localhost:3000/`.
- Verify: empty chat, existing chat selection, send/stream/cancel, image attachment preview/remove, settings open/close, dark/light theme, admin link visibility, no text overlap.
